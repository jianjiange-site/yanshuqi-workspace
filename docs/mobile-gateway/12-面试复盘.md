# mobile-gateway 面试复盘

简洁版，可直接口述。

---

## 1. 为什么要做 mobile-gateway？

App 只应面对 **一套 REST + 统一鉴权 + 统一错误码**。内部微服务是 gRPC + 多 proto，直接在客户端调 gRPC 不现实。gateway 把 **HTTP 世界和 gRPC 世界隔开**，并集中处理 JWT、参数转换、错误映射。

## 2. 为什么是 BFF，不是普通网关？

普通网关做路由和限流；我们还需要 **登录发 token、refresh 轮换、短信 mock、VO 组装**。这些状态在 gateway 的 PostgreSQL/Redis 里，已经超出“纯转发”。所以叫 BFF 更准确。

## 3. JWT 为什么放 gateway？

- 移动端只认 **一套 access token**。
- user-service 负责“是谁”（解析/创建用户），gateway 负责“怎么证明是本人”（RS256 签发、过期、logout 黑名单）。
- 业务接口统一从 JWT 取 `callerUserId`，避免每个服务重复解析 HTTP Header。

## 4. refresh token 为什么只存 hash？

数据库泄露时攻击者拿不到可用 refresh。验证时对请求 refresh 做 hash 比对；轮换时旧 token 标记 used，检测复用攻击（10504）。

## 5. logout 黑名单怎么做？

logout 把 access 的 `jti` 写入 Redis `gateway:auth:blacklist:{jti}`，TTL 到 token 自然过期。Filter 验 JWT 后查黑名单，命中则 10503。

## 6. post-service 为什么用 metadata 传 userId？

post proto 选择 **caller 走 gRPC metadata `x-user-id`**，与 match 的 request 字段方式不同。gateway 用 `GatewayGrpcMetadataSupport` 统一注入，并带上 traceId、deviceId 便于链路追踪。好处是 proto message 更干净，caller 与业务字段分离。

## 7. match-service 为什么 request 里带 callerUserId？

match 早期 proto 设计把 `caller_user_id` 放在每个 RPC request 里。gateway 从 JWT 解析后 **写入 request 字段**，同样禁止信任客户端传的 userId。两种风格并存，gateway 按下游契约适配，不强行统一。

## 8. gRPC 异常怎么映射成 REST Result？

GrpcClient 捕获 `StatusRuntimeException`，经 `GatewayGrpcExceptionMapper` 转成 `GatewayBizException`（如 UNAVAILABLE→10901，RESOURCE_EXHAUSTED→10520）。`GlobalExceptionHandler` 返回 HTTP 200 + `Result.code`。Filter 层鉴权失败才 HTTP 401。

## 9. Payment/IM 为什么不假装已完成？

payment-service 和 im-service 目前只有 **Stage 00-A 骨架**，没有正式 proto。如果在 prod 返回 mock 商品或 mock IM token，前端会以为能支付/能聊天，联调和上线会埋雷。GW-5 策略：**接口契约在，prod 明确 10701/108xx，mock 只在 mock/test profile**。

## 10. 技术难点与解法

| 难点 | 解法 |
| --- | --- |
| JWT 与 gRPC caller 一致性 | Filter 写 ThreadLocal；Resolver 只读 JWT |
| Post metadata 注入 | `MetadataUtils.newAttachHeadersInterceptor` + 通用 Support |
| refresh 复用攻击 | DB used_at + 错误码 10504 |
| 下游未就绪的 Payment/IM | Profile 隔离 prod vs mock；明确错误码 |
| WebMvcTest 与 JWT Filter | AuthConfiguration 单独 Import；Jwt 测试独立类 |

---

**一句话总结**：mobile-gateway 是移动端的 BFF，Auth/Match/Post 已闭环 gRPC；Payment/IM 只做了契约和边界，等下游 proto 就绪再替换 not ready。
