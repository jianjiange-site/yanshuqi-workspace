# PostService 项目地图

## 模块背景

PostService（`post-service`）是 Dating App 的 **UGC 内容域微服务**，负责帖子发布、详情、用户列表、点赞评论互动、推荐 Feed。学员标识 `yanshuqi`，PostgreSQL schema 为 `post_center`，Redis key 统一 `yanshuqi:` 前缀。

## 服务定位

- **是什么**：用户发帖与内容消费的独立微服务，对外暴露 gRPC `PostService`（9 个 RPC）。
- **不是什么**：不是网关、不是用户资料服务、不是 IM 通知服务、不是复杂推荐引擎。

## 上下游边界

| 方向 | 服务 | 关系 |
|------|------|------|
| 上游（预期） | mobile-gateway | REST → gRPC，解析 JWT / 注入 `x-user-id`（**未实现**） |
| 下游（预期） | user-service | 性别分桶、好友列表（**当前 fallback**） |
| 下游（无） | im-service | 未接通知 |
| 存储 | PostgreSQL | `post_center` 五张业务表 |
| 存储 | Redis | 详情缓存、计数 delta、Feed 池、timeline、已读 Set |
| 对象存储 | MinIO | 仅存 `image_key`，URL 由 gateway/CDN 拼装（post-service 不拼 URL） |

## 为什么当前没有开发 gateway

1. **阶段拆分**：post-service 先独立完成契约、主链路、互动、Feed，降低联调复杂度。
2. **可独立验收**：通过 gRPC Metadata `x-user-id` + Debug REST 完成全链路回归，不依赖 JWT。
3. **边界清晰**：鉴权、聚合、Swagger 文档归 gateway；内容域逻辑归 post-service。

## 学习价值

- 业务主键（`post_id` / `comment_id`）与 Snowflake 发号
- 点赞幂等 `(user_id, post_id)` + `ON CONFLICT`
- Redis 增量计数 + Lua 原子刷盘 + DB 基准值合并读
- Feed 三路混排（热门 / 时间线 / 冷启动）与已读去重
- 防腐层 `UserProfileClient` 隔离外部依赖
- Flyway 分阶段建表、MyBatis-Plus 单表访问

## 核心包结构

```text
com.dating.post/
├── grpc/           # PostGrpcService、用户上下文拦截器
├── controller/     # Health + internal/debug REST
├── service/        # 业务编排
├── manager/        # 单表聚合读写
├── mapper/         # MyBatis-Plus
├── entity/         # 表实体
├── repository/     # Redis 访问
├── job/            # 定时刷盘 / Feed 重建
├── client/         # UserProfileClient + fallback
├── constant/       # 状态、Redis key
└── dto/            # 内部传输对象
```
