# 03_STAGE_PLAN：ChatVibe / Dating App 生产级开发阶段计划

> 本文档用于把 ChatVibe / Dating App 后端项目拆成可交给 Cursor 分阶段执行的开发路线。  
> 本轮开发策略：**跳过 MVP 版本，直接按生产级完整闭环建设**。  
> 但“生产级一步到位”不等于一次性生成所有代码，而是按业务闭环逐阶段落地，每个阶段必须可运行、可联调、可验收、可回滚。

---

## 0. 开发策略总则

### 0.1 本次开发不走 MVP 路线

本项目不再划分“先做 MVP、后续再扩展”的主线，而是采用生产级阶段推进：

```text
先搭工程底座与契约治理
↓
再按真实业务闭环逐阶段实现
↓
每个阶段都满足生产级代码规范、数据规范、接口规范、幂等规范、日志规范、联调规范
↓
最终形成完整 Dating App 后端系统
```

因此，本文档中的 **P0 Production** 表示本轮生产级必做内容；**P1 Enhancement** 只表示可以晚于核心上线的增强项，不再表示 MVP 之后才做。

### 0.2 Cursor 执行原则

每个阶段交给 Cursor 时，只允许实现当前阶段定义的业务闭环，不允许越界生成其他模块。

Cursor 每阶段必须输出：

1. 本阶段完成内容。
2. 变更文件清单。
3. 新增 / 修改接口清单。
4. 新增 / 修改数据表和 Flyway 文件。
5. 新增 / 修改 Redis key。
6. 新增 / 修改 Nacos 配置。
7. 服务间 gRPC 调用链。
8. 幂等、事务、异常、日志处理说明。
9. 本地启动命令。
10. 自动化测试与人工验收步骤。
11. 未完成项、风险项、下一阶段依赖。

### 0.3 技术红线

以下红线所有阶段都不能违反：

| 红线 | 说明 |
|---|---|
| 禁止跨服务查库 | 每个服务只能访问自己的表、自己的 Flyway history、自己的 repository |
| 禁止服务间 HTTP 互调 | 服务之间统一 gRPC，只有 App / Webhook / 健康检查允许 REST |
| 禁止业务服务绕过 im-service | match / user / post / payment 不能直接调用 OpenIM REST，不能持有 OpenIM admin secret |
| 禁止业务工程复制 proto | proto 只能在 proto 仓库维护，stub 通过 Nexus 依赖引入 |
| 禁止 Redis 当最终数据源 | Redis 只做缓存、队列、配额、锁、热点池，最终事实必须落 PostgreSQL |
| 禁止多表 JOIN | MyBatis-Plus 只做单表 CRUD，跨表组装在 service 层完成 |
| 禁止生产路径 BeanUtils.copyProperties | DTO / Entity 转换手写或 MapStruct |
| 禁止跨服务事务 | 一致性通过幂等、outbox、重试、补偿、对账解决 |
| 禁止真实密钥入库 | PayPal、OpenIM、LiveKit、JWT、LLM key 只能走 env / Nacos |
| 禁止一次性大爆炸开发 | 每阶段只实现一个业务闭环，验收通过后进入下一阶段 |

## Stage 00：项目基线与共享基建接入

### 阶段目标

建立完整工程骨架，但不实现业务逻辑。目标是让所有服务都具备生产级基础能力：启动、配置加载、健康检查、日志、Docker、Nacos 配置、PostgreSQL 连接、Redis 连接、MinIO 配置、OpenIM 配置占位。

### 业务闭环

本阶段是基础闭环：

```text
开发者拉取项目
↓
配置本地 dev 环境
↓
启动 Java 服务 / ai-chat / OpenIM 依赖
↓
服务注册到 Nacos
↓
健康检查通过
↓
日志可在本地或 Loki 查看
```

### 涉及服务

| 服务 | 本阶段动作 |
|---|---|
| mobile-gateway | 建立 Spring Boot 启动、REST 健康检查、Nacos 配置加载 |
| user-service | 建立 Spring Boot 启动、PostgreSQL / Redis 连接 |
| match-service | 建立 Spring Boot 启动、Redis / PostgreSQL 连接 |
| im-service | 建立 OpenIM / LiveKit 配置占位、健康检查 |
| post-service | 建立 PostgreSQL / Redis / MinIO 配置 |
| payment-service | 建立 PostgreSQL、PayPal 配置占位 |
| ai-chat | 建立 Python gRPC 服务启动骨架、环境变量加载 |
| proto | 建立 proto 仓库目录规范 |

### 接口

| 类型 | 接口 | 说明 |
|---|---|---|
| REST | `GET /health` | 每个 Java 服务健康检查 |
| REST | `GET /actuator/health` | Spring Boot actuator 健康检查 |
| gRPC | 暂不实现业务 RPC | 只预留 server/client 配置 |

### 数据表

本阶段只允许创建 Flyway 基线表，不创建业务表。

| 服务 | Flyway history |
|---|---|
| mobile-gateway | `flyway_history_gateway` |
| user-service | `flyway_history_user` |
| match-service | `flyway_history_match` |
| im-service | `flyway_history_im` |
| post-service | `flyway_history_post` |
| payment-service | `flyway_history_payment` |

### Redis Key

本阶段不创建业务 key，只验证连接。

### 外部依赖

| 依赖 | 检查点 |
|---|---|
| PostgreSQL 16 | 每个服务可连接自己的 schema / database |
| Redis 7 | 可 ping，可读写测试 key 后删除 |
| Nacos 2.4 | dev namespace 可加载配置 |
| MinIO | 可列 bucket 或通过 SDK 连接 |
| Docker | 本地服务可容器化启动 |
| Loki / Grafana | 日志采集路径预留 |

### 验收标准

1. 所有服务能本地启动。
2. 所有 Java 服务健康检查返回 UP。
3. ai-chat gRPC 端口可监听。
4. 服务配置不写死公网 IP 和真实密钥。
5. Nacos dev namespace 可加载配置。
6. 每个服务日志包含 serviceName、traceId 占位、环境标识。
7. Docker Compose 可启动基础依赖。

### 人工检查点

- 检查是否有真实密码、token、secret 进仓库。
- 检查是否有服务直接访问其他服务数据库的配置。
- 检查所有服务是否使用 UTC。
- 检查 Redis key 是否已约定前缀。
- 检查每个服务是否有独立 Flyway history。

### Cursor 执行边界

只允许搭工程骨架和配置，不允许实现注册、匹配、IM、Feed、支付、AI 业务。

## Stage 01：Proto 契约与 gRPC 基线

### 阶段目标

建立跨服务、跨语言接口契约体系。Java 服务和 Python ai-chat 不直接拷贝 proto，而是通过 proto 仓库生成 stub 并发布到 Nexus。

### 业务闭环

```text
定义 proto 契约
↓
生成 Java / Python stub
↓
发布到 Nexus
↓
Java 服务引入 proto 依赖
↓
ai-chat 引入 Python proto 依赖
↓
通过 Nacos 发现服务
↓
完成一次 gRPC health / ping 调用
```

### 涉及服务

| 服务 | 本阶段动作 |
|---|---|
| proto | 定义所有服务的 proto module 和 version |
| user-service | 提供基础 UserProfileService ping / mock 方法 |
| im-service | 提供基础 ImService ping / mock 方法 |
| match-service | 提供基础 MatchService ping / mock 方法 |
| post-service | 提供基础 PostService ping / mock 方法 |
| payment-service | 提供基础 PaymentService ping / mock 方法 |
| ai-chat | 提供 ChatAgent / VisionAgent gRPC server skeleton |
| mobile-gateway | 建立 gRPC client 发现与调用基线 |

### 接口

| proto module | 初始服务 |
|---|---|
| `user.proto` | `UserIdentityService`、`UserProfileService`、`RecommendationService` |
| `im.proto` | `ImService`、`OpenImCallbackService`、`LiveKitService` |
| `match.proto` | `MatchService`、`MatchQueryService` |
| `post.proto` | `PostService`、`FeedService` |
| `payment.proto` | `CoinService`、`PaymentService`、`SubscriptionService` |
| `ai_chat.proto` | `ChatAgent`、`VisionAgent` |

### 数据表

无业务表。

### Redis Key

无业务 key。

### 外部依赖

| 依赖 | 用途 |
|---|---|
| Nexus | 发布 Java / Python / TypeScript stub |
| Nacos | gRPC 服务注册发现 |
| CI | proto 变更后自动构建 stub |

### 验收标准

1. proto 仓库可以生成 Java / Python stub。
2. stub 不能被复制到业务工程源码目录。
3. Java 服务通过 Maven 依赖引入 stub。
4. ai-chat 通过 Python 包方式引入 stub。
5. mobile-gateway 可以通过 Nacos 发现 user-service 并完成一次 gRPC 调用。
6. im-service 可以通过 Nacos 或配置直连 ai-chat 完成一次 ping 调用。
7. 所有 gRPC client 设置 deadline。
8. gRPC 错误码有统一转换策略。

### 人工检查点

- 检查业务仓库是否复制了 `.proto` 文件。
- 检查是否在业务工程里运行 protoc。
- 检查 gRPC client 是否写死 IP。
- 检查接口命名是否符合领域语义，而不是按数据库表命名。

### Cursor 执行边界

只做契约、stub、client/server 基线，不实现业务细节。

## Stage 02：注册登录与 Token 闭环

### 阶段目标

实现用户快速登录、手机号登录、三方登录预留、access token / refresh token、设备登记、OpenIM 用户注册、IM token 获取、注册赠送金币。

### 业务闭环

```text
App 请求发送验证码
↓
mobile-gateway 写 Redis 验证码和冷却 key
↓
App 提交验证码登录
↓
mobile-gateway 调 user-service 创建或查询用户身份
↓
mobile-gateway 登记设备与 refresh token
↓
mobile-gateway 调 im-service 注册 OpenIM 用户并获取 imToken
↓
mobile-gateway 调 payment-service 发放注册奖励 60 金币
↓
返回 accessToken + refreshToken + userId + imToken
```

### 涉及服务

| 服务 | 职责 |
|---|---|
| mobile-gateway | REST 登录入口、验证码、JWT、refresh token、设备登记 |
| user-service | 用户身份创建、手机号绑定、用户类型初始化 |
| im-service | OpenIM 用户注册、IM token 获取、lazy-register |
| payment-service | 注册奖励金币发放，幂等处理 |
| OpenIM | 底层 IM 用户与 token |

### 接口

| 类型 | 接口 | 说明 |
|---|---|---|
| REST | `POST /api/v1/auth/send-sms-code` | 发送验证码 |
| REST | `POST /api/v1/auth/login-phone` | 手机号验证码登录 |
| REST | `POST /api/v1/auth/refresh` | refresh token 轮换 |
| REST | `POST /api/v1/auth/logout` | access token 拉黑、refresh token 作废 |
| gRPC | `UserIdentityService.LoginOrCreateByPhone` | 创建或查询用户 |
| gRPC | `ImService.RegisterImUser` | 注册 OpenIM 用户 |
| gRPC | `ImService.GetImToken` | 获取 imToken |
| gRPC | `CoinService.GrantReward` | 注册奖励金币 |

### 数据表

| 服务 | 表 | 用途 |
|---|---|---|
| mobile-gateway | `auth_device` | 设备登记，唯一索引 `(user_id, device_id)` |
| mobile-gateway | `auth_refresh_token` | refresh token hash、轮换链、reuse detection |
| user-service | `user_identity` | 手机号、三方登录、用户主身份 |
| user-service | `user_profile` | 用户基础资料初始化 |
| payment-service | `coin_account` | 金币账户初始化 |
| payment-service | `coin_ledger` | 注册奖励流水 |
| payment-service | `reward_grant_record` | 奖励发放幂等 |

### Redis Key

| Key | TTL | 用途 |
|---|---:|---|
| `gateway:auth:sms:code:{phoneE164}` | 5 min | 验证码 |
| `gateway:auth:sms:cooldown:{phoneE164}` | 60 s | 防短信轰炸 |
| `gateway:auth:blacklist:{jti}` | token 剩余有效期 | access token 拉黑 |
| `user:profile:{userId}` | 30 min | 用户基础资料缓存，登录后可预热 |

### 外部依赖

| 依赖 | 用途 |
|---|---|
| Redis | 验证码、冷却、JWT 黑名单 |
| PostgreSQL | 用户身份、设备、refresh token、金币账户 |
| OpenIM | 用户注册与 IM token |
| payment-service | 注册奖励 |

### 生产级要求

1. Access token 使用 RS256。
2. Refresh token 不是 JWT，只存 SHA-256 hash。
3. Refresh token 每次刷新必须轮换。
4. 已 used refresh token 再次提交要触发 reuse detection。
5. OpenIM 注册必须幂等，已存在视为成功。
6. 注册奖励必须幂等，不能重复发 60 金币。
7. 登录链路中 im-service 异常要有明确策略：可登录但提示 IM 初始化中，或 fail-fast，必须产品确认后固定。

### 验收标准

1. 新手机号首次登录成功，生成用户、设备、金币账户、注册奖励流水。
2. 同手机号重复登录不重复创建用户，不重复发注册奖励。
3. refresh token 可轮换，旧 refresh token 再用会被识别。
4. logout 后 access token 进入 Redis 黑名单。
5. OpenIM 用户已注册，可获取 imToken。
6. 返回结果不包含任何敏感密钥。

### 人工检查点

- 检查 token 是否入库明文。
- 检查注册奖励是否有唯一幂等键。
- 检查 user-service 是否没有处理 JWT。
- 检查 payment-service 是否没有被 gateway 直接查表。
- 检查 OpenIM admin secret 是否只在 im-service。

### Cursor 执行边界

只实现登录注册闭环，不实现用户资料完善、推荐、匹配、聊天。

## Stage 03：用户资料完善与任务奖励闭环

### 阶段目标

实现用户基础资料完善、标签、位置、Bio、职业、身高、体重、教育、MBTI 等资料更新，并通过一次性任务发放资料完善奖励金币。

### 业务闭环

```text
用户提交基础资料
↓
mobile-gateway 鉴权后转 user-service
↓
user-service 校验字段、更新 user_profile / user_preference / user_tag
↓
user-service 判断资料完善任务是否首次完成
↓
user-service 调 payment-service 发放奖励金币
↓
payment-service 写金币流水和奖励记录
↓
user-service 删除用户资料缓存
↓
返回资料完成度与奖励结果
```

### 涉及服务

| 服务 | 职责 |
|---|---|
| mobile-gateway | 鉴权、REST 入参校验、转发 gRPC |
| user-service | 用户资料、偏好、资料完成度、任务状态 |
| payment-service | 任务奖励金币发放 |

### 接口

| 类型 | 接口 | 说明 |
|---|---|---|
| REST | `GET /api/v1/profile/me` | 查询我的资料 |
| REST | `PUT /api/v1/profile/basic` | 更新基础资料 |
| REST | `PUT /api/v1/profile/preferences` | 更新择偶偏好 |
| REST | `GET /api/v1/profile/completion` | 查询资料完成度 |
| gRPC | `UserProfileService.GetProfile` | 查询用户资料 |
| gRPC | `UserProfileService.UpdateBasicProfile` | 更新基础资料 |
| gRPC | `UserProfileService.UpdatePreference` | 更新偏好 |
| gRPC | `CoinService.GrantReward` | 资料完善奖励 |

### 数据表

| 服务 | 表 | 用途 |
|---|---|---|
| user-service | `user_profile` | 昵称、性别、年龄、Bio、职业、身高、体重、教育、MBTI |

| `match:quota:{userId}:{yyyymmdd}` | HASH | 36 h | 划卡配额 |
| `match:swiped:{userId}` | SET | 永久 | 已划集合 |
| `lock:match:swipe:{user}:{target}` | RLock | 5 s | 划卡串行化 |
| `lock:match:dh-delay:{taskId}` | RLock | 30 s | 延迟任务执行防重 |

### 外部依赖

| 依赖 | 用途 |
|---|---|
| im-service | 发送欢迎消息 |
| ai-chat | DH 开场白 |
| Redis / DB | 延迟任务防重与持久化 |

### 生产级要求

1. 生产级不建议只使用进程内 TaskScheduler，服务重启会丢任务；必须落库或使用可恢复延迟任务机制。
2. 延迟任务必须幂等，同一个 BH-DH 只能创建一次 match。
3. DH 延迟时间要可配置，并支持随机区间。
4. DH 开场白失败不能影响 match 创建。
5. 系统消息发送失败通过 outbox 重试。

### 验收标准

1. 右划 DH 后不会立即创建 match。
2. 延迟时间到达后创建 match。
3. 服务重启后未执行延迟任务仍可恢复。
4. 重复任务不会重复创建 match。
5. 匹配后收到欢迎消息或 DH 开场消息。
6. ai-chat 失败时仍保留匹配关系。

### 人工检查点

- 检查是否只用内存延迟任务。
- 检查 DH 任务是否有状态机：PENDING / PROCESSING / DONE / FAILED。
- 检查 match 唯一约束是否兜底。
- 检查开场白失败是否阻塞主流程。

### Cursor 执行边界

只实现 DH 延迟匹配，不实现 AI 多轮聊天、不实现 IM 消息扣费。

## Stage 09：IM 文字消息与金币扣费闭环

### 阶段目标


## Stage 10：AI Chat 数字人回复闭环

### 阶段目标

实现 BH 给 DH 发消息后，im-service 在 after-send 回调中触发 ai-chat ChatAgent，ai-chat 拉取双方资料、读取上下文、生成回复，im-service 分句按节奏发送回 OpenIM。

### 业务闭环

```text
BH 给 DH 发送消息
↓
OpenIM after-send 回调
↓
im-service 写 chat_messages
↓
im-service 判断 route_type = BH_DH
↓
TEXT 直接作为 message，IMAGE 先调用 VisionAgent.Understand
↓
im-service 调 ai-chat.ChatAgent.Chat(threadId, from, to, message)
↓
ai-chat 调 user-service 拉 BH / DH 用户上下文
↓
ai-chat 使用 LangGraph checkpoint 读取历史
↓
ai-chat 生成回复
↓
im-service 分句、延迟、顺序发送 AI 消息到 OpenIM
↓
im-service 写入或等待 after-send 写入 AI 消息记录
```

### 涉及服务

| 服务 | 职责 |
|---|---|
| im-service | AI 路由、消息转换、分句发送、兜底 |
| ai-chat | ChatAgent、VisionAgent、LangGraph、LLM 调用 |
| user-service | 用户上下文查询 |
| OpenIM | AI 消息投递 |
| PostgreSQL | LangGraph checkpointer |

### 接口

| 类型 | 接口 | 说明 |
|---|---|---|
| gRPC | `ChatAgent.Chat` | 数字人回复 |
| gRPC | `VisionAgent.Understand` | 图片消息理解 |
| gRPC | `UserProfileService.BatchGetProfile` | 拉 BH / DH 用户档案 |
| gRPC | `ImService.SendMessage` | 发送 AI 消息，或 im-service 内部 OpenIM sender |

### 数据表

| 服务 | 表 | 用途 |
|---|---|---|
| im-service | `chat_messages` | BH / DH 消息记录 |
| ai-chat | `langgraph_checkpoints` | 多轮上下文 |
| ai-chat | `ai_chat_run_log` | AI 调用日志，建议生产级保留 |

### Redis Key

| Key | 类型 | TTL | 用途 |
|---|---|---:|---|
| `im:ai:replying:{threadId}` | STRING | 60 s | 防同线程重复并发回复 |
| `ai-chat:circuit:{provider}` | STRING | 30 s | Vision / Chat 模型熔断状态，可选 |

### 外部依赖

| 依赖 | 用途 |
|---|---|
| DeepSeek / Chat LLM | 文本回复 |
| Vision LLM | 图片理解 |
| PostgreSQL checkpointer | 多轮上下文 |
| user-service | 用户资料上下文 |
| OpenIM | 发送 AI 回复 |

### 生产级要求

1. ai-chat 不直接访问 Java 服务数据库，必须通过 user-service gRPC 拉资料。
2. threadId 固定使用一对用户维度，确保多轮上下文连续。
3. ai-chat 失败不能影响用户聊天主流程。
4. 同一 threadId 要避免并发回复乱序。
5. 图片理解失败要降级为占位文本。
6. AI 回复内容要做基础安全和反导流过滤。
7. LLM 调用日志不能记录敏感 token。

### 验收标准

1. BH 给 DH 发文本消息后，DH 能自动回复。
2. 同一对用户多轮聊天有上下文记忆。
3. BH 给 DH 发图片后，VisionAgent 先生成图片描述，再交给 ChatAgent。
4. ai-chat 故障时，BH 消息仍然发送成功。
5. AI 回复分句按顺序发送。
6. AI 消息不触发金币扣费。

### 人工检查点

- 检查 ai-chat 是否直接查 user-service 数据库。
- 检查 threadId 是否稳定。
- 检查异常时是否吞掉用户消息。
- 检查 AI 回复是否绕过 im-service 直接调 OpenIM。

### Cursor 执行边界

只实现 DH 数字人回复，不实现 Post 内容生成、不实现支付。

## 20. 学习使用方式

每个阶段你都不要只看 Cursor 生成的代码是否能跑，而要按以下顺序复盘：

1. 先讲清楚这个阶段的业务闭环。
2. 再画出入口接口到最终落库的调用链。
3. 再列出涉及服务和服务边界。
4. 再说明每张表为什么归属于这个服务。
5. 再说明每个 Redis key 的用途、TTL 和可重建性。
6. 再说明哪个动作需要幂等，幂等键是什么。
7. 再说明失败时如何重试、补偿或降级。
8. 最后总结成面试表达。

本项目最终不是为了证明“AI 能生成代码”，而是要证明你能讲清楚：

```text
业务怎么跑
服务怎么拆
数据怎么流
调用怎么走
缓存怎么用
失败怎么兜
钱和金币怎么保证不乱
IM 和 AI 怎么接入真实业务
```
