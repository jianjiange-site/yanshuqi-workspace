# 02服务边界说明

> 本文档用于在开发前明确每个服务的职责边界、数据边界、接口边界和工程红线。
>
> 它不写代码，不替代 proto 接口文档，也不替代数据库设计文档。它解决的问题是：**这件事应该放在哪个服务里做，不能放在哪个服务里做，服务之间应该怎么调用，哪些边界不能突破。**

---

## 0. 边界总原则

ChatVibe 后端采用 Java 微服务 + Python Agent + OpenIM 的架构。服务边界必须优先按业务领域划分，而不是按页面、表、接口数量或开发方便程度划分。

### 0.1 一句话原则

```text
App 只访问 mobile-gateway；
业务服务之间默认走 gRPC；
每个服务只操作自己的库表、Redis key、对象存储前缀；
OpenIM / LiveKit 只能由 im-service 封装；
ai-chat 只提供 AI 能力，不接管业务状态。
```

### 0.2 服务边界判断标准

当你不知道一段逻辑应该放在哪个服务时，按下面顺序判断：

1. **这段逻辑最终改变哪个领域的核心业务状态？**  
   改用户资料，放 user-service；改匹配关系，放 match-service；改金币账本，放 payment-service。

2. **这段逻辑依赖哪个领域的主表？**  
   依赖 `user_info` 是用户域；依赖 `match_relation` 是匹配域；依赖 `coin_ledger` 是支付域。

3. **这段逻辑是否只是入口层聚合？**  
   只是鉴权、参数转换、REST 转 gRPC、聚合多个服务结果，放 mobile-gateway。

4. **这段逻辑是否涉及 OpenIM / LiveKit admin 能力？**  
   涉及消息发送、IM token、OpenIM 回调、LiveKit token，一律放 im-service。

5. **这段逻辑是否是大模型推理、图像理解、数字人回复？**  
   放 ai-chat，但 ai-chat 不直接写 Java 业务库。

6. **这段逻辑是否涉及余额、扣费、流水、订阅、支付回调？**  
   一律放 payment-service，其他服务只能通过 gRPC 发起消费或查询。

### 0.3 数据所有权原则

| 领域 | 数据所有者 | 其他服务访问方式 |
|---|---|---|
| 登录设备、refresh token、JWT 黑名单 | mobile-gateway | 不允许直接访问；通常无需跨服务查询 |
| 用户身份、资料、头像、兴趣、城市、用户类型 | user-service | 通过 user-proto gRPC 查询 |
| 推荐队列、划卡记录、匹配关系、配额、DH 延迟任务 | match-service | 通过 match-proto gRPC 查询或操作 |
| IM 消息历史、在线状态、OpenIM/LiveKit 封装状态 | im-service | 通过 im-proto gRPC 操作 |
| 帖子、图片、点赞、评论、Feed 池、Post 计数 | post-service | 通过 post-proto gRPC 操作 |
| 金币账户、金币流水、订阅、订单、支付回调 | payment-service | 通过 payment-proto gRPC 操作 |
| AI 对话上下文、LangGraph checkpoint、AI 推理结果 | ai-chat | 通过 chat-proto / vision-proto gRPC 调用 |

禁止一个服务直接读写另一个服务的 PostgreSQL 表、Redis key、MinIO bucket 目录或第三方密钥。

## 1. mobile-gateway 服务边界

### 1.1 服务定位

mobile-gateway 是移动端 App 的唯一业务入口，定位是 **BFF / REST 网关 / 鉴权网关 / 请求路由层**。

它负责把移动端友好的 REST 接口转换为内部标准 gRPC 调用，同时完成登录、鉴权、token 管理、参数转换、错误码适配和少量聚合查询。

### 1.2 负责什么

| 职责 | 说明 |
|---|---|
| 对 App 暴露 REST API | App 的业务接口统一访问 mobile-gateway，例如登录、资料、推荐、划卡、帖子、支付入口 |
| 登录入口 | 接收手机号登录、第三方登录、设备登录请求 |
| 验证码能力 | 发送验证码、验证码缓存、防短信轰炸冷却 |
| JWT 签发与校验 | 签发 access token；管理 refresh token；校验请求鉴权上下文 |
| refresh token 轮换 | refresh token 入库只存 hash；刷新时轮换；重复使用触发 reuse detection |
| token 黑名单 | 用户登出或强制下线时，将 access token jti 写入 Redis 黑名单 |
| 请求上下文透传 | 从 JWT 中提取 userId、deviceId、traceId，通过 gRPC metadata 传给下游 |
| REST 参数转换 | 将 REST JSON DTO 转换为 proto request |
| gRPC 结果适配 | 将下游 gRPC 响应转换成 App 需要的 REST JSON |
| 简单 BFF 聚合 | 例如首页卡片详情可以并发调 user-service 和后续关系服务做聚合 |
| OpenIM 回调入口转发 | 接收 OpenIM callback HTTP 请求，做 IP 白名单校验，然后转发给 im-service 的 `onRawCallback` |
| 健康检查与网关级限流 | 对外健康检查、基础限流、上传大小限制配合 Nginx |

### 1.3 不负责什么

| 不负责 | 原因 |
|---|---|
| 不沉淀用户主档案 | 用户资料属于 user-service，gateway 不能维护 `user_info` 主数据 |
| 不实现推荐算法 | 推荐队列、D0/D1、排序、配额属于 match-service |
| 不创建匹配关系 | 匹配关系是 match-service 的核心状态 |
| 不直接扣金币 | 金币账户和流水只能由 payment-service 修改 |
| 不直接调 OpenIM admin 接口发送业务消息 | OpenIM admin secret 只能由 im-service 持有 |
| 不直接调用 LiveKit 生成 token | LiveKit token 统一由 im-service 生成 |
| 不保存聊天消息 | 消息历史由 im-service 管理 |
| 不做 AI 推理 | 数字人回复、图片理解、颜值评分由 ai-chat 提供 |
| 不跨服务查库做聚合 | 聚合可以通过 gRPC，并发查服务；不能直接 JOIN 其他服务表 |
| 不写复杂业务状态机 | 状态机应该留在对应领域服务内 |

### 1.4 拥有的数据

| 表 / Key | 说明 |
|---|---|
| `auth_device` | 设备指纹、登录设备登记 |
| `auth_refresh_token` | refresh token hash、轮换链路、reuse detection |
| `gateway:auth:sms:code:{phoneE164}` | 手机验证码，短 TTL |
| `gateway:auth:sms:cooldown:{phoneE164}` | 验证码发送冷却 |
| `gateway:auth:blacklist:{jti}` | access token 黑名单 |

### 1.5 典型调用链

```text
App 登录请求
  ↓ REST
mobile-gateway
  ↓ gRPC
user-service.ResolveOrCreateByPhone
  ↓
user-service.CheckBan
  ↓
mobile-gateway 写 auth_device / auth_refresh_token
  ↓
mobile-gateway 签发 access token / refresh token
  ↓
新用户异步或同步弱依赖调用 im-service.registerImUser
```

### 1.6 Cursor 开发边界提示

交给 Cursor 开发 mobile-gateway 时，必须强调：

- 只做 REST controller、auth filter、gRPC client、DTO/proto 转换、token 管理。
- 不允许在 gateway 里写 match / post / payment 的核心业务逻辑。
- 不允许 gateway 直接访问其他服务的表。
- 下游服务失败时要有明确错误映射，不要吞异常。
- 新用户注册 IM 失败不能阻塞登录，但必须记录日志和可重试线索。

## 2. user-service 服务边界

### 2.1 服务定位

user-service 是用户域服务，负责 **用户身份解析、用户档案、头像资料、兴趣标签、城市信息、用户类型和推荐召回所需用户画像**。

它是较纯粹的数据服务，不应该主动编排复杂跨领域业务。

### 2.2 负责什么

| 职责 | 说明 |
|---|---|
| 身份解析 | 手机号、第三方账号、设备匿名登录解析为统一 userId |
| 新用户占位档案 | 首次登录时创建 pending 状态的 `user_info` 占位记录 |
| 封禁状态查询 | `CheckBan` 判断用户是否被封禁或暂停 |
| Onboarding | 用户首次完善昵称、性别、生日、城市等资料 |
| 日常资料编辑 | 修改昵称、简介、兴趣、头像等允许修改的字段 |
| 性别 / 生日等关键字段限制 | 首次填写后是否可改由 user-service 规则控制 |
| 头像上传签名 | 生成 avatar 上传 presigned URL；确认上传后写入 object_key |
| 用户兴趣标签 | 维护 `user_interest`，支持全量替换 |
| 用户资料查询 | `GetProfile`、`BatchGetProfile`，供 gateway、match、im、ai-chat 调用 |
| 推荐召回候选 | 给 match-service 提供 DH 候选、附近 BH 候选、城市替换等召回 RPC |
| 用户类型判断 | 判断 BH / DH，用于 IM 路由和匹配策略 |
| 用户资料缓存 | 维护 `user:profile:*` 等缓存，写后删除缓存 |

### 2.3 不负责什么

| 不负责 | 原因 |
|---|---|
| 不负责 JWT 签发 | token 是 gateway 的入口层职责 |
| 不负责 refresh token 存储 | refresh token 属于 gateway 登录态 |
| 不负责推荐队列生成 | user-service 只提供候选查询，不决定最终推荐顺序和队列 |
| 不负责划卡行为 | swipe 是 match-service 的核心行为 |
| 不负责匹配关系创建 | match_relation 归 match-service |
| 不负责聊天消息 | IM 消息由 im-service 和 OpenIM 处理 |
| 不负责金币余额 | 金币账户、流水归 payment-service |
| 不负责 AI 评分算法本身 | 可以保存 AI 分析结果，但推理由 ai-chat 执行 |
| 不负责 Feed 内容 | 帖子、评论、点赞由 post-service 管理 |
| 不主动调用 OpenIM | 注册 IM 用户由 im-service 封装，user-service 不持有 OpenIM secret |

### 2.4 拥有的数据

| 表 / Key | 说明 |
|---|---|
| `user_info` | 用户主档案；包含 user_type、gender、age、city、beauty_score、pending 等 |
| `user_login_phone` | 手机号绑定 |
| `user_third_party_registration` | 第三方账号绑定 |
| `user_device_registration` | 设备匿名账号绑定 |
| `user_interest` | 用户兴趣标签 |
| `geo_city` | 城市字典 |
| `user:profile:{userId}` | 用户资料缓存 |
| `user:profile:big:{userId}` | 用户大资料缓存 |
| `user:interest:{userId}` | 兴趣缓存 |
| `user:ban:status:{userId}` | 封禁状态缓存 |
| `lock:user:register:*` | 注册防重复锁 |

### 2.5 对外 gRPC 能力

| 服务接口 | 典型方法 | 调用方 |
|---|---|---|
| UserIdentityService | `ResolveOrCreateByPhone`、`ResolveOrCreateByThirdParty`、`ResolveOrCreateByDevice`、`CheckBan` | mobile-gateway |
| UserProfileService | `GetProfile`、`BatchGetProfile`、`UpdateProfile`、`UpsertOnboarding`、`ReplaceUserInterests`、`PresignAvatarUpload`、`ConfirmAvatarUpload` | mobile-gateway、match-service、im-service、ai-chat |
| RecommendationService | `ListDhCandidates`、`NearbyUsers`、`PickDhCitiesForCaller` | match-service |

### 2.6 典型调用链

```text
App 完善资料
  ↓ REST
mobile-gateway
  ↓ gRPC
user-service.UpsertOnboarding
  ↓
校验必填字段、年龄、性别、城市、昵称
  ↓
事务更新 user_info + user_interest
  ↓
删除 user:profile:* / user:interest:* 缓存
  ↓
返回完整用户资料
```

### 2.7 Cursor 开发边界提示

交给 Cursor 开发 user-service 时，必须强调：

- user-service 是用户主数据服务，不写匹配、支付、IM 核心逻辑。
- 登录创建用户时必须用分布式锁 + 唯一索引兜底，防止重复账号。
- 写用户资料后必须删除相关缓存。
- 出参只返回 object_key，不拼 CDN URL，不返回永久签名 URL。
- `BatchGetProfile` 要去重保序，避免 N+1 查询。
- 召回接口只负责“提供候选”，最终排序、配额、队列归 match-service。

## 3. match-service 服务边界

### 3.1 服务定位

match-service 是推荐与匹配引擎，负责 **推荐队列、划卡、配额、匹配关系、DH 延迟匹配、Super Hi、Like / Visit 相关匹配策略**。

这是 Dating App 最核心的业务服务之一。

### 3.2 负责什么

| 职责 | 说明 |
|---|---|
| D0 冷启动推荐 | 新用户或队列为空时实时构造推荐队列 |
| D1 日更推荐 | 每天根据历史划卡行为生成个性化队列 |
| 推荐队列消费 | 从 `match:feed:{userId}` 取卡片，二次过滤已划过、已 block、状态异常用户 |
| 划卡行为 | LEFT / RIGHT 行为记录、幂等判断、配额扣减 |
| 匹配关系创建 | BH 互相右划立即匹配；DH 右划进入延迟匹配；Super Hi 立即匹配 |
| DH 延迟匹配 | 对 DH 目标延迟 15s~2min 后创建匹配，模拟真人节奏 |
| Super Hi | 订阅赠送配额或金币扣费后立即匹配 |
| Like / Visit | 生成 Like / Visit 记录，支持用户付费解锁或触发匹配 |
| 配额控制 | 每日卡片数、右划数、Super Hi 赠送次数，按订阅档位计算 |
| 推荐偏好建模 | 根据右划历史计算年龄、颜值、种族、DH/BH 比例偏好 |
| 匹配成功通知 | 调 im-service 发送系统消息或业务通知 |
| 匹配相关幂等 | swipe 幂等、match 唯一约束、Super Hi requestId 幂等 |

### 3.3 不负责什么

| 不负责 | 原因 |
|---|---|
| 不维护用户主档案 | 用户资料属于 user-service，match 只能通过 gRPC 查询 |
| 不直接修改用户金币账户 | 扣金币必须通过 payment-service `ConsumeCoins` |
| 不直接调用 OpenIM | 系统消息、会话创建、通知发送必须通过 im-service |
| 不负责聊天消息收发 | 聊天由 im-service / OpenIM 管理 |
| 不负责 AI 数字人回复 | DH 开场白或回复由 im-service 调 ai-chat，match 不直接做 AI 推理 |
| 不负责帖子 Feed | 内容推荐归 post-service，匹配推荐归 match-service |
| 不负责支付订单 | 支付、订阅、金币流水归 payment-service |
| 不跨库查 user/post/payment 表 | 跨领域数据通过 gRPC 获取 |

### 3.4 拥有的数据

| 表 / Key | 说明 |
|---|---|
| `swipe_record` | 用户划卡记录，包含方向、目标、时间、幂等信息 |
| `match_relation` | 匹配关系，通常用双方 userId 排序后唯一约束防重复 |
| `like_visit_record` | Like / Visit 相关记录，视实现阶段决定是否拆分 |
| `match_outbox` | 匹配成功后的消息通知重试 outbox |
| `match:feed:{userId}` | 推荐队列 LIST |
| `match:quota:{userId}:{yyyymmdd}` | 每日配额 HASH |
| `match:swiped:{userId}` | 已划过目标 SET |
| `match:pref:{userId}` | 用户推荐偏好 HASH |
| `lock:match:d1:{yyyymmdd}` | D1 队列任务分布式锁 |
| `lock:match:swipe:{user}:{target}` | 单次 swipe 串行锁 |

### 3.5 依赖的外部服务

| 依赖 | 目的 |
|---|---|
| user-service | 获取候选用户、用户资料、用户类型、城市替换信息 |
| payment-service | 查询订阅档位、Super Hi 扣金币、获取配额相关权益 |
| im-service | 创建会话、发送匹配成功系统消息、发送业务通知 |
| Redis | 推荐队列、配额、已划集合、偏好缓存、分布式锁 |
| PostgreSQL | 划卡记录、匹配关系、outbox 等最终事实数据 |

### 3.6 对外 gRPC 能力

| 方法 | 说明 | 调用方 |
|---|---|---|
| `GetTodayFeed` | 获取今日推荐卡片，队列不足时触发冷启动补队列 | mobile-gateway |
| `Swipe` | 处理左划 / 右划、配额、幂等、匹配创建 | mobile-gateway |
| `SuperHi` | 处理 Super Hi 配额 / 扣费 / 立即匹配 | mobile-gateway |
| `ListMatches` | 查询我的匹配列表 | mobile-gateway |
| `GetQuota` | 查询今日配额与使用情况 | mobile-gateway |

### 3.7 典型调用链

```text
用户右划一个 BH 真人
  ↓ REST
mobile-gateway
  ↓ gRPC
match-service.Swipe
  ↓
校验配额 + 幂等 + 是否已划过
  ↓
写 swipe_record + Redis match:swiped
  ↓
查询对方是否也右划过我
  ├─ 没有：只记录行为
  └─ 有：创建 match_relation
          ↓
          调 im-service.ensureConversation / sendBusinessNotification
```

```text
用户右划一个 DH 数字人
  ↓
match-service.Swipe
  ↓
写 swipe_record
  ↓
调度 DH 延迟任务 15s~2min
  ↓
延迟任务触发
  ↓
创建 match_relation
  ↓
调 im-service 发送匹配成功消息 / DH 开场白触发
```

### 3.8 Cursor 开发边界提示

交给 Cursor 开发 match-service 时，必须强调：

- match-service 可以调用 user/payment/im 的 gRPC，但不能查它们的表。
- swipe 必须具备幂等能力，重复请求不能重复扣配额、重复创建匹配。
- 匹配关系必须有唯一约束兜底，不能只依赖代码判断。
- Redis 队列只是推荐缓存，最终划卡和匹配结果必须落 PostgreSQL。
- Super Hi 扣金币必须传 `clientRequestId` 生成幂等键，例如 `superhi:{clientRequestId}`。
- DH 延迟匹配 MVP 可以用进程内调度，后续再升级为 Redis 延迟队列 / MQ / XXL-JOB。

## 4. im-service 服务边界

### 4.1 服务定位

im-service 是 OpenIM + LiveKit 的业务编排中枢，负责 **IM 用户注册、IM token、消息回调、消息扣费、反导流、AI Chat 路由、系统消息、业务通知、LiveKit token**。

它不实现底层 WebSocket，也不替代 OpenIM，而是把 OpenIM / LiveKit 包装成可控的业务能力。

### 4.2 负责什么

| 职责 | 说明 |
|---|---|
| OpenIM 用户注册 | 为业务 userId 注册 OpenIM 用户；处理已存在的幂等成功 |
| OpenIM token 下发 | App 登录后通过 gateway 获取 IM token |
| OpenIM 回调处理 | 处理 before-send、after-send、online、offline 等回调 |
| 消息前置校验 | before-send 阶段做反导流、余额准入、是否允许发送 |
| 消息扣费编排 | 调 payment-service 查询余额和消费金币，幂等键使用消息 ID |
| 消息历史记录 | after-send 阶段落 `chat_messages` |
| BH / DH 路由识别 | 调 user-service 判断发送方和接收方用户类型 |
| AI Chat 触发 | BH 给 DH 发消息后，异步调用 ai-chat 生成回复 |
| AI 回复发送 | 将 AI 回复分句、延迟、通过 OpenIM REST 发回用户 |
| 系统消息发送 | 给 match-service 等上游提供发送系统消息 / 业务通知能力 |
| 业务通知 | match_success、match_welcome、typing 等自定义业务通知 |
| LiveKit token | 为 1v1 音视频生成房间 token |
| 在线状态 | 处理 OpenIM 上线 / 下线回调，记录在线时长和 Redis presence |

### 4.3 不负责什么

| 不负责 | 原因 |
|---|---|
| 不自研 IM WebSocket | 底层消息连接由 OpenIM SDK / OpenIM Server 提供 |
| 不直接决定用户是否匹配 | 匹配关系由 match-service 创建 |
| 不维护金币账户 | 只能调用 payment-service 扣费，不能自己改余额 |
| 不维护用户资料 | 只能调用 user-service 查询用户类型和资料 |
| 不实现 AI Agent 内部逻辑 | AI 推理和上下文由 ai-chat 负责 |
| 不处理支付订单 | PayPal / IAP / 订阅属于 payment-service |
| 不处理帖子、Feed、评论 | 内容归 post-service |
| 不让其他服务绕过自己直连 OpenIM | OpenIM admin secret 只能在 im-service 内使用 |

### 4.4 拥有的数据

| 表 / Key | 说明 |
|---|---|
| `chat_messages` | 消息历史，记录 OpenIM 消息 ID、双方 userId、内容、类型、路由类型 |
| `user_online_session` | 用户在线时长会话 |
| `im:presence:online` | 在线用户 ZSet |
| OpenIM admin secret | 只能由 im-service 持有，不能下发到其他业务服务 |
| LiveKit API key / secret | 只能由 im-service 使用，用于签发 token |

### 4.5 依赖的外部服务

| 依赖 | 目的 |
|---|---|
| OpenIM Server | 用户注册、token 获取、发送消息、业务通知、回调来源 |
| LiveKit | 1v1 音视频房间 token |
| user-service | 查询用户类型、用户资料 |
| payment-service | 查询余额、消息扣费 |

| PostgreSQL | 消息历史、在线会话 |
| Redis | 在线状态、必要的短期状态 |

### 4.6 对外 gRPC 能力

| 方法 | 说明 | 调用方 |
|---|---|---|
| `onRawCallback` | 接收 gateway 转发的 OpenIM raw callback | mobile-gateway |
| `registerImUser` | 注册 OpenIM 用户 | mobile-gateway、user-service 相关链路 |
| `getImToken` | 获取 OpenIM token | mobile-gateway |
| `sendMessage` | 业务服务主动发送普通消息 | match-service 等 |
| `sendBusinessNotification` | 发送业务通知，如匹配成功、欢迎语、typing | match-service |
| `generateCallToken` | 生成 LiveKit 1v1 音视频 token | mobile-gateway |

### 4.7 典型调用链

```text
用户 A 给用户 B 发送消息
  ↓
OpenIM before-send callback
  ↓ HTTP
mobile-gateway /callback/openim/{cmd}
  ↓ gRPC
im-service.onRawCallback
  ↓
im-service 判断发送方类型
  ├─ DH：直接放行
  ├─ BH 且反导流命中：拒绝
  └─ BH 且付费聊天：调 payment-service 查余额
       ├─ 不足：拒绝
       └─ 足够：放行，并异步 ConsumeCoins(im-msg:{messageId})
```

```text
BH 给 DH 发消息后
  ↓
OpenIM after-send callback
  ↓
im-service 落 chat_messages
  ↓
im-service 判断 route_type = BH_DH
  ↓
im-service 调 ai-chat.Chat(threadId=from:to)
  ↓
ai-chat 返回回复
  ↓
im-service 分句 + 延迟
  ↓
im-service 调 OpenIM REST send_msg 发回用户
```

### 4.8 Cursor 开发边界提示

交给 Cursor 开发 im-service 时，必须强调：

- 不实现 WebSocket，不替代 OpenIM。
- before-send 必须快速返回，耗时逻辑尽量异步。
- payment-service 故障时消息扣费场景按策略 fail-close，避免免费绕过。
- `ConsumeCoins` 幂等键必须使用稳定 messageId，例如 `im-msg:{messageId}`。
- after-send 触发 AI 回复不能阻塞 OpenIM 回调成功响应。
- AI 回复消息要避免再次触发扣费或反导流误伤。
- OpenIM admin secret / LiveKit secret 不能暴露给其他服务。

## 5. post-service 服务边界

### 5.1 服务定位

post-service 是内容与 Feed 服务，负责 **发帖、删帖、图片关联、点赞、评论、帖子详情、用户帖子列表、推荐 Feed、好友时间线、热门池、冷启动池、计数写合并**。

它解决的是“内容消费”问题，不解决“恋爱匹配关系”问题。

### 5.2 负责什么

| 职责 | 说明 |
|---|---|
| 发帖 | 创建帖子、关联最多 9 张图片、初始化统计记录 |
| 删除帖子 | 作者删除、软删、清理缓存和 Feed 池引用 |
| 帖子详情 | 查询帖子、图片、统计、当前用户是否点赞 |
| 用户帖子列表 | 查询某个用户的帖子列表 |
| 点赞 / 取消点赞 | 点赞幂等、状态切换、Redis 增量计数 |
| 评论 | 创建评论、删除评论、评论列表缓存 |
| Post 计数 | like_count / comment_count Redis 增量，定时 flush 回 PostgreSQL |
| 冷启动池 | 新帖进入冷启动池，让新内容有曝光机会 |
| 热门推荐池 | 根据热度公式定时计算推荐池 |
| 好友时间线 | 发帖后 fanout 到粉丝或好友 timeline |
| Feed 三路融合 | 推荐池 + 好友时间线 + 冷启动池混排 |
| 已读去重 | 使用 Bloom Filter 或其他机制避免重复刷同一批内容 |
| 图片 object_key 管理 | 只保存 MinIO object_key，不保存永久签名 URL |

### 5.3 不负责什么

| 不负责 | 原因 |
|---|---|
| 不维护用户资料 | 作者昵称、头像等通过 user-service 查询或由前端已有上下文补足 |
| 不创建匹配关系 | 内容互动不等于恋爱匹配，匹配归 match-service |
| 不处理 IM 聊天 | 评论和 IM 是两套业务 |
| 不扣金币 | 付费查看、解锁等若后续有，需要通过 payment-service |
| 不做 AI 图片审核主逻辑 | 可预留审核状态，但 AI 识别能力由 ai-chat 或审核服务提供 |
| 不直接访问 match-service 表 | 如果需要好友/匹配关系，必须通过 match-service gRPC 或后续关系服务 |
| 不处理支付订单 | 支付归 payment-service |

### 5.4 拥有的数据

| 表 / Key | 说明 |
|---|---|
| `post` | 帖子主表 |
| `post_image` | 帖子图片表，保存 object_key |
| `post_stat` | 帖子统计基准值 |
| `post_like` | 点赞关系，保证点赞幂等 |
| `post_comment` | 评论表 |
| `post:detail:{postId}` | 帖子详情缓存 |
| `post:stat:incr:{postId}:likes` | 点赞增量计数 |
| `post:stat:incr:{postId}:comments` | 评论增量计数 |
| `updated_posts_set` | 待刷盘的帖子集合 |
| `user:timeline:{userId}` | 用户时间线 |
| `feed:cold_start:pool:{gender}` | 冷启动池 |
| `feed:pool:recommend:{gender}` | 推荐池 |
| `post:comments:{postId}` | 评论缓存 |
| `user:read:bloom:{userId}` | 已读去重 |

### 5.5 对外接口能力

post-service 可以同时提供 gRPC 和受控 REST，但在本项目微服务协作中，**App 业务入口仍应通过 mobile-gateway**。

| 能力 | gRPC | REST | 调用方 |
|---|---|---|---|
| 创建帖子 | `CreatePost` | `POST /v1/posts` | mobile-gateway / 内部测试 |
| 帖子详情 | `GetPostDetail` | `GET /v1/posts/{postId}` | mobile-gateway |

```text

  ↓ REST
mobile-gateway
  ↓ gRPC
```

### 5.7 Cursor 开发边界提示

交给 Cursor 开发 post-service 时，必须强调：

- 点赞必须幂等，重复点赞不能重复加计数。
- Redis 计数只是增量缓存，最终要刷回 PostgreSQL。
- 删除帖子必须清缓存、清 Feed 池引用，但不要物理删除业务记录。
- 发帖只保存图片 object_key，不保存本地文件路径。
- Feed 推荐和 match 推荐是两个不同领域，不要混到 match-service。
- MVP 可以先做发帖、列表、点赞、评论；推荐池和 Bloom 去重可以后续扩展。

## 6. payment-service 服务边界

### 6.1 服务定位

payment-service 是金币、订阅、支付和流水服务，负责 **金币账户、金币流水、订阅权益、支付订单、PayPal Webhook、消费幂等、余额查询、权益查询**。

它是所有“钱”和“权益”的最终事实源。

### 6.2 负责什么

| 职责 | 说明 |
|---|---|
| 金币账户 | 维护免费金币、付费金币、总余额、乐观锁版本 |
| 金币流水 | 所有收入 / 消费写 append-only ledger，不能只改余额不记流水 |
| 金币消费 | 提供 `ConsumeCoins`，支持幂等键、余额校验、分层扣减 |
| 金币发放 | 新人奖励、后台奖励、支付成功发放付费金币 |
| 订阅权益 | 维护 FREE / WEEKLY / MONTHLY / YEARLY 等订阅档位和有效期 |
| 权益查询 | 给 match-service 查询每日配额档位，给其他服务查询付费能力 |
| 支付订单 | 创建订单、记录第三方订单号、订单状态、支付渠道 |
| PayPal 集成 | 创建 PayPal order、capture、Webhook 验签与处理 |
| 支付回调幂等 | 同一第三方交易不能重复发金币或重复开通订阅 |
| 对账与可追溯 | 通过订单表和流水表追踪每一笔金币变化 |

### 6.3 不负责什么

| 不负责 | 原因 |
|---|---|
| 不决定用户能看到谁 | 推荐策略归 match-service |
| 不决定消息是否允许发送 | im-service 根据业务场景调用 payment-service 做余额和扣费 |
| 不直接发送 IM 系统消息 | 系统消息归 im-service |
| 不维护用户资料 | 用户资料归 user-service |
| 不创建匹配关系 | 匹配归 match-service |
| 不处理帖子业务 | 内容归 post-service |
| 不做 AI 推理 | AI 归 ai-chat |
| 不把余额字段散落到其他服务 | 其他服务只缓存权益或查询结果，不保存最终余额 |

### 6.4 拥有的数据

| 表 | 说明 |
|---|---|
| `coin_accounts` | 用户金币账户，免费余额、付费余额、version |
| `coin_ledger` | 金币流水，append-only，含 idempotency_key |
| `user_subscription` | 用户订阅档位和过期时间 |
| `payment_orders` | 支付订单，第三方交易号和状态 |

### 6.5 对外 gRPC / REST 能力

| 能力 | 协议 | 说明 | 调用方 |
|---|---|---|---|
| `GetCoins` | gRPC | 查询用户金币余额 | im-service、mobile-gateway |
| `ConsumeCoins` | gRPC | 消费金币，必须带幂等键 | im-service、match-service |
| `AddCoins` | gRPC | 发放免费金币 | admin / 新人奖励链路 |
| `AddPaidCoins` | gRPC | 发放付费金币 | 支付成功后内部调用 |
| `GetCoinLedger` | gRPC | 查询金币流水 | mobile-gateway / admin |
| `CreateOrder` | gRPC | 创建支付订单 | mobile-gateway |
| `VerifyPayment` | gRPC | 主动校验支付结果 | mobile-gateway |
| `GetSubscription` | gRPC | 查询订阅档位和有效期 | match-service |
| PayPal Webhook | REST | 接收第三方支付平台回调 | PayPal → payment-service |

### 6.6 典型调用链

```text
用户发送付费 IM 消息
  ↓
im-service before-send
  ↓
payment-service.GetCoins
  ↓
余额足够
  ↓
im-service 放行消息
  ↓
im-service 异步调用 payment-service.ConsumeCoins(idempotencyKey="im-msg:{messageId}")
  ↓
payment-service 乐观锁扣余额 + 写 coin_ledger
```

```text
用户购买金币
  ↓ REST
mobile-gateway
  ↓ gRPC
payment-service.CreateOrder
  ↓
创建 payment_orders INIT
  ↓
调用 PayPal 创建订单
  ↓
用户完成支付
  ↓
PayPal Webhook → payment-service REST
  ↓
验签 + 幂等判断
  ↓
更新订单 PAID
  ↓
AddPaidCoins + 写 coin_ledger
```

### 6.7 Cursor 开发边界提示

交给 Cursor 开发 payment-service 时，必须强调：

- 余额变化必须有流水，不能只 update `coin_accounts`。
- 所有消费必须带 idempotency_key。
- `coin_ledger` 要有唯一约束兜底重复消费。
- 扣费要使用乐观锁或事务锁，避免并发超扣。
- PayPal Webhook 必须验签、幂等、可重试。
- 其他服务不能复制一份余额字段自行判断最终余额。

## 7. ai-chat 服务边界

### 7.1 服务定位

ai-chat 是 Python Agent 服务，负责 **DH 数字人聊天、聊天上下文、意图识别、图片理解、颜值评分、资料照分析**。

它通过 gRPC 被 Java 业务服务调用，是“AI 能力服务”，不是业务主状态服务。

### 7.2 负责什么

| 职责 | 说明 |
|---|---|
| ChatAgent | 根据 BH/DH 用户资料、聊天上下文和用户输入生成数字人回复 |
| VisionAgent | 图片理解、头像分析、颜值评分、资料照质量分析 |
| LangGraph 编排 | 管理聊天状态、意图识别、动态提示词、工具调用流程 |
| LangChain 模型调用 | 封装 LLM、Vision LLM、模型路由、熔断和降级 |
| 对话上下文 | 使用 threadId 维护一对用户的多轮聊天上下文 |
| 用户上下文拉取 | 通过 user-service gRPC 获取用户资料，不直接查 user 数据库 |
| AI 失败兜底 | 模型失败时返回兜底回复或明确错误，不能让上游阻塞 |
| 图片文本化 | IM 图片消息可转成描述后交给 ChatAgent 理解 |

### 7.3 不负责什么

| 不负责 | 原因 |
|---|---|
| 不对 App 暴露 REST | AI 只能由业务服务通过 gRPC 调用 |
| 不直接发送 OpenIM 消息 | 消息发送由 im-service 调 OpenIM 完成 |
| 不决定消息是否扣费 | 扣费由 im-service + payment-service 完成 |
| 不创建匹配关系 | 匹配由 match-service 完成 |
| 不维护金币余额 | 金币归 payment-service |
| 不直接写 user-service 数据表 | 用户资料归 user-service |
| 不决定用户封禁 / 审核状态 | 风控和用户状态由业务服务维护 |
| 不保存业务最终状态 | AI 只保存自身 checkpoint / trace / 推理上下文 |

### 7.4 拥有的数据

| 数据 | 说明 |
|---|---|
| LangGraph checkpoint | 以 threadId 区分会话上下文 |
| AI 调用日志 / trace | 可接 LangSmith 或本地日志 |
| Prompt 模板 | system prompt、意图识别 prompt、图片理解 prompt |
| 模型路由配置 | DeepSeek、Vision 模型、熔断、降级策略 |

### 7.5 对外 gRPC 能力

| 服务 | 方法 | 说明 | 调用方 |
|---|---|---|---|
| ChatAgent | `Chat` | 数字人聊天回复 | im-service |
| VisionAgent | `Understand` | 图片理解 | im-service / user-service 相关链路 |
| VisionAgent | `ScoreFace` | 颜值评分 | user-service 头像分析链路 |
| VisionAgent | `AnalyzeProfilePhoto` | 资料照分析 | user-service 头像分析链路 |

### 7.6 典型调用链

```text
BH 给 DH 发文本消息
  ↓
im-service after-send callback
  ↓
im-service 判断 route_type = BH_DH
  ↓
im-service 调 ai-chat.Chat(threadId="BH:DH", fromUserId, toUserId, message)
  ↓
ai-chat 通过 user-service 获取双方资料
  ↓
LangGraph 加载 checkpoint
  ↓
LLM 生成回复
  ↓
保存 checkpoint
  ↓
返回文本给 im-service
```

```text
用户上传头像后确认
  ↓
user-service 记录 object_key
  ↓
后续触发 VisionAgent.AnalyzeProfilePhoto / ScoreFace
  ↓
ai-chat 返回图片质量、颜值评分、风险标签
  ↓
user-service 保存分析结果或更新资料状态
```

### 7.7 Cursor 开发边界提示

交给 Cursor 开发 ai-chat 时，必须强调：

- Python 服务只实现 gRPC servicer，不直接暴露 App REST。
- 不直接连 Java 业务数据库；用户资料通过 user-service gRPC 获取。
- AI 失败要有兜底，不要让 im-service 回调线程长时间阻塞。
- threadId 要稳定，例如 `{fromUserId}:{toUserId}`，保证多轮上下文可复用。
- prompt、模型配置、熔断参数要配置化，不要硬编码在业务逻辑里。
- LangGraph checkpoint 只保存 AI 会话状态，不保存支付、匹配等业务最终状态。

## 8. 哪些事情必须通过 gRPC

### 8.1 服务间业务调用默认必须 gRPC

| 场景 | 必须 gRPC 的原因 |
|---|---|
| gateway 调 user / match / im / post / payment | 内部服务调用，统一 proto 契约、错误码、deadline、metadata |
| match-service 查询用户资料 | 用户资料归 user-service，不能查用户表 |
| match-service 查询订阅 / 扣 Super Hi 金币 | 支付权益归 payment-service，必须走 CoinService / PaymentService |
| match-service 发送匹配成功通知 | OpenIM 能力归 im-service，必须走 im-proto |
| im-service 查询用户类型 | BH/DH 类型归 user-service，必须走 user-proto |
| im-service 扣消息金币 | 金币账户归 payment-service，必须走 payment-proto |
| im-service 调数字人回复 | AI 服务是 Python gRPC，必须走 chat-proto |
| ai-chat 查询用户资料 | ai-chat 不查 Java DB，必须走 user-service gRPC |
| post-service 如需用户资料补全 | 只能调用 user-service gRPC，不跨库查 user_info |
| payment-service 被其他服务消费金币 | 只能通过 `ConsumeCoins`，不能暴露表给别人改 |

### 8.2 gRPC 调用要求

| 要求 | 说明 |
|---|---|
| proto 契约优先 | 先定义 proto，再生成 Java / Python stub |
| 版本锁定 | 业务服务依赖明确版本，不用 LATEST / RELEASE / 范围版本 |
| Nacos 服务发现 | 不硬编码内部服务 IP；通过 Nacos 找健康实例 |
| deadline | 每次下游调用设置超时，例如 3s |
| metadata 透传 | userId、deviceId、traceId 通过 metadata 传递 |
| 标准错误码 | 用 gRPC status 或统一错误模型，不要随意塞字符串 |
| 幂等键 | 涉及扣费、支付、消息、匹配创建时必须传稳定幂等键 |
| 降级策略 | AI、IM、支付等关键依赖失败时要明确 fail-open 或 fail-close |

## 9. 哪些事情可以走 REST

REST 只用于边界入口、第三方回调、健康检查、对象上传直传和局部调试，不用于常规服务间业务调用。

| 场景 | 是否可以 REST | 说明 |
|---|---|---|
| App 调业务接口 | 可以，且必须先到 mobile-gateway | App 不直接访问内部服务 gRPC |
| OpenIM 回调到业务系统 | 可以 | OpenIM 以 HTTP callback 调 gateway，然后 gateway 转 gRPC 给 im-service |
| PayPal Webhook | 可以 | 第三方支付平台只能 HTTP 回调 payment-service 或经网关转发 |
| 健康检查 / Actuator | 可以 | `/actuator/health`、容器健康检查、Nginx 检查 |
| MinIO presigned PUT 上传 | 可以 | App 拿签名 URL 后直传对象存储，业务服务只保存 object_key |
| post-service REST | 受控可以 | 用于内部测试或兼容，但 App 正常仍应经 gateway |
| payment-service REST Webhook | 可以 | 第三方支付回调用 REST，不属于内部业务互调 |
| Swagger / 本地调试 | 可以 | dev 环境可以保留，但生产入口要受控 |

### 9.1 REST 不能滥用的场景

以下场景不要走 REST：

| 禁止 REST 的场景 | 应该使用 |
|---|---|
| gateway 调 user-service 创建用户 | gRPC |
| match-service 查询 user-service 候选人 | gRPC |
| im-service 调 payment-service 扣费 | gRPC |
| ai-chat 查询用户资料 | gRPC |
| match-service 调 im-service 发通知 | gRPC |
| post-service 获取用户资料 | gRPC |
| 任意服务直接 HTTP 调 OpenIM | 只能 im-service 内部封装 OpenIM REST |

## 10. 哪些红线不能碰

### 10.1 架构红线

| 红线 | 说明 |
|---|---|
| App 不能直接访问内部业务服务 | App 只能访问 mobile-gateway 和 OpenIM / LiveKit SDK 所需地址 |
| 服务间业务调用禁止随意 HTTP 互调 | 默认 gRPC，REST 只用于边界入口和第三方回调 |
| 禁止跨服务查库 | user-service 不能查 match 表，match-service 不能查 user 表 |
| 禁止一个服务写另一个服务的 Redis key | Redis key 有服务前缀和归属，不允许偷写 |
| 禁止复制 `.proto` 到业务工程 | proto 独立仓库管理，业务工程通过 Nexus 依赖 stub |
| 禁止业务工程本地手动跑 protoc 生成线上依赖 | stub 由 proto 仓 CI 发布，业务服务锁版本使用 |
| 禁止硬编码内部服务 IP | 服务发现走 Nacos，配置走 Nacos/env |
| 禁止绕过 im-service 直连 OpenIM / LiveKit | admin secret 和 LiveKit secret 只能由 im-service 持有 |
| 禁止 ai-chat 直接写 Java 业务库 | AI 服务通过 gRPC 获取上下文，只保存自身 checkpoint |
| 禁止 Redis 作为最终数据源 | Redis 数据必须可以从 PostgreSQL 或业务事实重建 |

### 10.2 数据库红线

| 红线 | 说明 |
|---|---|
| 禁止多服务共用一批业务表 | 每个服务拥有自己的表和 Flyway history |
| 禁止跨服务 JOIN | 微服务内不做跨域 JOIN，跨域组装在 service 层通过 gRPC 完成 |
| 禁止只 update 余额不写流水 | 金币变化必须写 `coin_ledger` |
| 禁止物理删除核心业务数据 | 用户、帖子、匹配、订单、流水默认逻辑删除或状态流转 |
| 禁止没有唯一约束的幂等设计 | 支付、扣费、匹配、划卡必须有数据库唯一约束兜底 |
| 禁止把 URL 当对象存储主数据 | 入库只存 object_key，不存临时签名 URL |
| 禁止本地时间混乱 | 统一 UTC 时间，展示层再转时区 |

### 10.3 Redis 红线

| 红线 | 说明 |
|---|---|
| 禁止无 TTL 的临时缓存 | 验证码、黑名单、缓存、Feed 池等必须明确 TTL |
| 禁止多个服务共用模糊 key | key 必须带服务前缀，例如 `match:*`、`post:*`、`gateway:*` |
| 禁止只写缓存不写库 | 核心业务状态必须先落 PostgreSQL |
| 禁止缓存更新策略混乱 | 推荐 cache aside：先写库，再删缓存 |
| 禁止用 Redis 锁替代唯一约束 | 分布式锁只是降低并发冲突，数据库唯一约束才是兜底 |

### 10.4 OpenIM / LiveKit 红线

| 红线 | 说明 |
|---|---|
| 禁止其他服务持有 OpenIM admin secret | 只能 im-service 持有 |
| 禁止 match-service 直接调 OpenIM 发送匹配消息 | 必须调 im-service |
| 禁止 gateway 直接实现 IM 业务逻辑 | gateway 只转发 callback，业务由 im-service 做 |
| 禁止自研一套 WebSocket 聊天替代 OpenIM | 本项目学习重点是集成与封装，不是重造 IM |
| 禁止 LiveKit token 在客户端或其他服务签发 | 统一由 im-service 签发 |

### 10.5 支付红线

| 红线 | 说明 |
|---|---|
| 禁止绕过 payment-service 扣金币 | 所有消费必须走 `ConsumeCoins` |
| 禁止没有幂等键的扣费 | IM 消息、Super Hi、支付回调都必须有稳定幂等键 |
| 禁止支付回调不验签 | PayPal / IAP / Stripe 等必须验证来源 |
| 禁止重复发放金币或订阅 | 订单状态、第三方交易号、流水唯一键必须兜底 |
| 禁止用前端支付结果直接发权益 | 前端只能触发校验，最终以服务端回调 / 验证为准 |

### 10.6 AI 红线

| 红线 | 说明 |
|---|---|
| 禁止 AI 直接决定业务最终状态 | AI 可以分析和生成，但不能直接扣费、匹配、封禁 |
| 禁止把用户隐私无控制地塞进 prompt | prompt 上下文要最小必要化 |
| 禁止 AI 失败阻塞核心业务链路 | AI 回复失败应兜底，不能拖垮 OpenIM 回调 |
| 禁止 prompt 和模型 key 写死在代码 | 使用 Nacos/env 管理配置和密钥 |
| 禁止让 ai-chat 直接访问 payment/match/user 数据库 | 跨服务数据通过 gRPC 获取 |

### 10.7 共享基建红线

| 红线 | 说明 |
|---|---|
| 禁止提交真实密码 / key | 任何密钥不能 commit 到业务仓库 |
| 禁止共用别人 Nacos namespace | 每个学员 / 环境使用独立 namespace |
| 禁止共用别人 PostgreSQL schema 或库 | 开发环境也要隔离，避免互相覆盖数据 |
| 禁止共用别人 MinIO bucket 前缀 | object_key 要带服务和用户前缀 |
| 禁止共用别人 RocketMQ topic | topic 要带个人或环境前缀 |
| 禁止 proto 包命名冲突 | groupId / Python package / npm package 必须带个人前缀或项目约定前缀 |

## 11. 服务边界总表

| 服务 | 负责 | 不负责 | 主要调用下游 | 数据归属 |
|---|---|---|---|---|
| mobile-gateway | REST 入口、鉴权、token、参数转换、gRPC 路由、OpenIM callback 转发 | 业务核心状态、跨服务查库、直接扣费、直接调 OpenIM | user、match、im、post、payment | auth_device、auth_refresh_token、gateway Redis key |
| user-service | 用户身份、资料、头像、兴趣、城市、用户类型、候选召回 | 推荐排序、匹配、金币、IM、Feed、AI 推理 | 基本无下游；必要时对象存储 | user_info、login binding、interest、city、user Redis key |
| match-service | 推荐队列、划卡、配额、匹配、DH 延迟、Super Hi | 用户主档案、金币账本、IM 底层、帖子、AI 推理 | user、payment、im | swipe、match、match Redis key |
| im-service | OpenIM/LiveKit 封装、消息回调、扣费编排、AI 路由、系统消息 | 匹配决策、用户主数据、金币账本、AI 内部推理 | user、payment、ai-chat、OpenIM、LiveKit | chat_messages、online_session、im Redis key |
| post-service | 发帖、点赞、评论、Feed、计数刷盘 | 匹配、聊天、金币、支付、用户主资料 | user 可选 | post、post_image、like、comment、post Redis key |
| payment-service | 金币账户、流水、订阅、订单、支付回调、扣费幂等 | 推荐、匹配、聊天发送、用户资料、AI | 第三方支付平台 | coin_accounts、coin_ledger、subscription、orders |
| ai-chat | 数字人回复、图片理解、颜值评分、LangGraph 上下文 | 业务状态、扣费、匹配、OpenIM 发送、用户库写入 | user-service、LLM | checkpoint、AI trace、prompt 配置 |

## 12. 按业务问题判断服务归属

| 问题 | 应放服务 | 原因 |
|---|---|---|
| 用户手机号第一次登录，创建 userId | user-service | 身份解析和用户占位档案归用户域 |
| 签发 access token / refresh token | mobile-gateway | 登录态和入口鉴权归网关 |
| 用户修改昵称和头像 | user-service | 用户资料主数据归用户域 |
| 用户上传头像后让 AI 评分 | user-service 编排或异步触发 ai-chat | 头像归用户域，AI 分析由 ai-chat 提供能力 |
| 首页推荐卡片列表 | match-service | 推荐队列和卡片消费归匹配域 |
| 用户右划一个真人 | match-service | 划卡记录和匹配关系归匹配域 |
| 用户右划一个数字人，过 1 分钟匹配 | match-service | DH 延迟匹配是匹配策略 |
| 匹配成功后发系统消息 | match-service 调 im-service | 匹配由 match 决定，消息由 im 发送 |
| 用户发聊天消息前判断金币 | im-service 调 payment-service | IM 判断消息场景，payment 管余额和扣费 |
| BH 给 DH 发消息后 AI 回复 | im-service 调 ai-chat | IM 识别路由并发送回复，AI 生成文本 |
| 用户发帖子 | post-service | 内容主数据归内容域 |
| 用户点赞帖子 | post-service | 点赞关系和计数归内容域 |
| 用户购买金币 | payment-service | 订单和金币归支付域 |
| PayPal 回调 | payment-service REST | 第三方支付回调归支付域 |
| 查询订阅影响右划次数 | match-service 调 payment-service | 配额使用归 match，订阅权益归 payment |

## 13. 后续开发使用建议

后续每个阶段交给 Cursor 前，都应该先带上本服务边界文档，并在提示词里明确：

1. 本阶段只做一个业务闭环。
2. 不允许新增跨服务查库。
3. 不允许把其他服务的核心逻辑写进当前服务。
4. 所有跨服务业务调用优先使用 gRPC client。
5. 当前阶段涉及哪些数据表、Redis key、外部依赖必须列清楚。
6. Cursor 完成后必须输出：
   - 改动文件列表
   - 新增接口列表
   - 调用链说明
   - 数据表变化
   - Redis key 变化
   - 外部依赖
   - 本地启动方式
   - 验收命令
   - 人工检查点

后续生成 `03_STAGE_PLAN.md` 时，应以本文档为边界约束，按真实业务闭环拆阶段，而不是按服务一次性生成所有代码。
