# 00_PROJECT_MAP：ChatVibe / Dating App 后端项目地图

> 本文档用于项目启动阶段建立全局认知。它不写代码，不展开详细接口和表结构，只回答：这个项目是什么、有哪些服务、依赖哪些基础设施、服务之间怎么协作，以及为什么适合作为后端微服务学习项目。

------

## 1. 项目背景

ChatVibe / Dating App 是一个面向陌生人社交与恋爱匹配的移动端产品。核心形态类似“资料展示 + 划卡推荐 + 匹配聊天 + 内容 Feed + 金币付费”的综合型 Dating App。

项目后端不是单体服务，而是基于 Java 微服务 + Python Agent + OpenIM 的完整后端体系：

- Java 侧负责主要业务服务：登录鉴权、用户资料、推荐匹配、IM 编排、Feed 内容、支付金币等。
- Python 侧负责 AI 能力：数字人聊天、头像/图片理解、颜值评分、资料照分析。
- OpenIM / LiveKit 负责 IM 与音视频底层能力，但业务侧不能直接绕过 im-service 使用它们。
- Proto / gRPC / Nacos 负责跨服务、跨语言通信与服务发现。
- PostgreSQL / Redis / MinIO / RocketMQ 等基础设施支撑数据持久化、缓存、对象存储和异步解耦。

从学习角度看，这不是一个“CRUD 项目”，而是一个比较完整的真实业务型后端项目：既有用户系统，又有推荐匹配、IM 扣费、AI Agent、内容 Feed、支付流水、缓存队列、延迟匹配、幂等、一致性、服务边界等综合问题。

------

## 2. 核心业务目标

### 2.1 产品层目标

项目要解决的是 Dating App 的完整闭环：

1. 用户可以注册、登录，并完善个人资料。
2. 用户可以上传头像和相册，系统通过 AI 做真人识别、图片理解和颜值评分。
3. 系统根据用户资料、偏好、划卡行为和推荐策略生成推荐队列。
4. 用户可以在首页进行左划、右划、Super Hi 等操作。
5. 真人用户之间在互相喜欢后可以立即匹配。
6. 真人用户与数字人之间不能直接立即匹配，需要通过 DH 延迟匹配策略控制节奏。
7. 匹配成功后用户可以聊天，聊天、礼物、解锁 Like / Visit、Super Hi 等行为和金币系统联动。
8. 数字人聊天由 AI Chat 接管，实现“像真人一样回复”的体验。
9. 用户可以发帖、点赞、评论，并通过推荐 Feed 浏览异性内容、好友内容和热门内容。
10. 用户可以通过支付购买金币或订阅权益，系统要维护金币余额、消费流水、订阅权益和幂等支付记录。

### 2.2 后端层目标

后端的目标不是简单提供接口，而是建立一套清晰的微服务协作体系：

1. mobile-gateway 作为移动端唯一公网入口，统一鉴权、参数校验和 REST 到 gRPC 的转发。
2. 各业务服务按照领域边界拆分，服务之间不能直接访问对方数据库。
3. 服务间调用统一使用 gRPC，接口契约统一由 proto 仓库维护并发布到 Nexus。
4. 配置与服务发现统一接入 Nacos。
5. 核心数据持久化统一使用 PostgreSQL。
6. Redis 只做缓存、队列、配额、锁和热点数据，不作为最终数据源。
7. OpenIM / LiveKit 只作为底层 IM/音视频引擎，所有业务语义由 im-service 封装。
8. AI Chat 作为独立 Python gRPC 服务，为 Java 业务侧提供 Agent 能力。

## 6. 服务依赖关系

### 6.1 总体调用原则

本项目的调用原则可以概括为：

```text
App REST 请求 → mobile-gateway → 内部 gRPC → 各业务服务 → PostgreSQL / Redis / MinIO
App IM 连接 → OpenIM SDK → OpenIM Server → 回调 mobile-gateway / im-service → 业务处理
IM 数字人消息 → im-service → ai-chat gRPC → user-service 拉上下文 → 返回 AI 回复
```

关键规则：

1. App 对业务接口只访问 mobile-gateway。
2. 服务之间默认走 gRPC，不走 HTTP。
3. 每个服务只访问自己的数据库表、Redis key 和对象存储 bucket。
4. 需要其他领域数据时，通过对方 gRPC 查询。
5. OpenIM / LiveKit 统一由 im-service 封装，其他业务服务不能绕过它。
6. ai-chat 是 Python gRPC 服务，由 im-service 或相关业务服务调用，不直接暴露给 App。

### 6.2 服务依赖矩阵

| 调用方          | 主要被调服务 / 系统                                          | 典型目的                                                     |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |

## 7. 项目学习价值

### 7.1 对 Java 后端开发者的价值

这个项目适合从“单服务业务开发”升级到“微服务业务架构开发”。你需要重点掌握：

1. 如何按领域拆服务，而不是按表或页面拆服务。
2. mobile-gateway 为什么只做入口、鉴权和编排，不沉淀核心业务。
3. user / match / im / post / payment 之间如何划清边界。
4. 服务之间为什么要用 gRPC，而不是直接 HTTP / Feign / RestTemplate。
5. 为什么每个服务只能访问自己的库表、Redis key 和对象桶。
6. 为什么 PostgreSQL 是最终事实源，Redis 只能做缓存、队列、锁和加速。
7. 为什么 IM 能力必须通过 im-service 封装，不能业务服务各自直连 OpenIM。
8. 为什么支付、金币、订阅要独立成 payment-service，并通过流水保证可追溯。

### 7.2 对微服务能力的价值

项目覆盖了典型微服务问题：

| 能力       | 项目中的体现                                                 |
| ---------- | ------------------------------------------------------------ |
| 服务边界   | 用户、匹配、IM、内容、支付、AI 分别独立建模                  |
| RPC 契约   | proto 统一定义，Java / Python / TypeScript 共享 stub         |
| 服务发现   | gRPC 服务通过 Nacos 注册与发现                               |
| 数据隔离   | 每个服务独立表、独立 Flyway history、禁止跨库跨表直连        |
| 缓存治理   | Redis key 前缀、TTL、cache aside、推荐队列、Feed 池          |
| 幂等设计   | 支付回调、金币消费、划卡、匹配创建、OpenIM 回调重复处理      |
| 最终一致性 | 扣费、会话创建、系统消息、Feed 计数刷盘、支付对账            |
| 定时任务   | D1 推荐队列、Like Visit 生成、Feed 热门池刷新、计数批量刷盘  |
| 降级兜底   | AI Chat 失败兜底、IM 失败不阻塞登录、Feed 池空兜底、支付回调重试 |

### 7.3 对 gRPC / Nacos / Proto 的价值

本项目不是只“会写接口”，而是要理解接口契约如何支撑多服务协作：

1. proto 是接口契约的唯一来源。
2. Java 服务和 Python ai-chat 通过同一套 proto 通信。
3. 业务工程不复制 proto 文件，也不在业务工程里手动跑 protoc。
4. proto stub 要发布到 Nexus，再由 Java / Python / TypeScript 按依赖拉取。
5. 服务地址不应写死，应该通过 Nacos discovery 查找。
6. gRPC 调用要关注 deadline、错误码、重试、降级和超时隔离。

### 7.4 对 Redis / PostgreSQL 的价值

项目里的 Redis 和 PostgreSQL 不是“随便用”：

- PostgreSQL 负责最终一致的业务数据，例如用户资料、匹配记录、帖子、评论、金币流水、订单。
- Redis 负责高频访问和短期状态，例如验证码、JWT 黑名单、推荐队列、Feed 池、点赞增量、配额、锁。
- Redis 里的状态必须能从 PostgreSQL 重建，不能把 Redis 当数据库。
- 写库和缓存一致性采用 cache aside，原则是先写库，再删缓存。
- 推荐队列、Feed 池、配额扣减、延迟匹配等是 Redis 的重点学习场景。

### 7.5 对 OpenIM 的价值

你不需要从零实现 IM，但必须掌握如何把开源 IM 引擎包装成业务能力：

1. 客户端通过 OpenIM SDK 建立消息连接。
2. OpenIM 负责底层消息投递。
3. OpenIM 回调进入业务系统后，im-service 才执行扣费、存档、AI 路由、风控等业务逻辑。
4. 业务服务不能直接持有 OpenIM admin secret。
5. 业务服务不能绕过 im-service 直接调 OpenIM REST。
6. LiveKit 只负责音视频底层能力，业务房间、Token、收费策略仍由 im-service / payment-service 编排。

### 7.6 对 Python Agent 的价值

ai-chat 是你从 Java 后端转向 Agent 开发的关键学习点：

1. ai-chat 不是独立玩具项目，而是通过 gRPC 嵌入真实业务系统。
2. ChatAgent 负责 DH 数字人回复，需要结合 BH / DH 双方资料和聊天上下文。
3. VisionAgent 负责头像分析、图片理解、颜值评分、资料照分析等多模态能力。
4. LangGraph checkpointer 负责聊天上下文持久化。
5. Java 侧通过 im-service 编排 AI 调用，Python 侧只提供 AI 能力，不越权处理支付、匹配、IM 引擎等业务。
6. 你可以学习“Java 业务系统 + Python Agent 服务”的真实企业级协作方式。

### 7.7 对面试表达的价值

这个项目最终应该沉淀成以下几类面试表达：

1. 我如何从 PRD 拆出注册、资料、推荐、匹配、IM、AI Chat、Feed、支付这些核心业务流。
2. 我如何划分 mobile-gateway、user-service、match-service、im-service、post-service、payment-service、ai-chat 的边界。
3. 我如何设计服务间调用，为什么统一使用 gRPC + Nacos + proto。
4. 我如何处理推荐队列、划卡、DH 延迟匹配、Super Hi、Like Visit 等 Dating App 特有业务。
5. 我如何设计 IM 消息扣费、OpenIM 回调幂等、AI Chat 回复和失败兜底。
6. 我如何设计金币账户、金币流水、支付回调幂等和订阅权益。
7. 我如何使用 Redis 做推荐队列、Feed 池、计数写合并、配额和分布式锁。
8. 我如何把 Python Agent 接入 Java 微服务，而不是停留在 Demo 层。

## 8. 本文档的使用方式

后续开发不要直接让 Cursor 一次性生成完整项目。建议按以下顺序推进：

1. 先确认本项目地图，保证你知道有哪些服务、业务和基础设施。
2. 再生成 `01_BUSINESS_FLOWS.md`，按真实业务流拆解用户操作、系统处理、数据流和技术难点。
3. 再生成 `02_SERVICE_BOUNDARY.md`，明确每个服务负责什么、不负责什么，以及服务间调用红线。
4. 再生成 `03_STAGE_PLAN.md`，按业务闭环拆阶段，每阶段只交给 Cursor 做一个可验收闭环。
5. 每个阶段 Cursor 完成后，必须输出调用链、变更文件、接口、数据表、Redis key、验收命令和人工检查点。
6. 你按调用链读代码，再用答辩问题检查自己是否真正理解。

本项目的学习目标不是“代码跑起来”，而是最终能够讲清楚：

- 业务流程
- 服务边界
- 技术架构
- 调用链
- 数据流
- 核心技术难点
- 为什么这么设计
- 有哪些替代方案
- 面试时如何表达
