# 01_BUSINESS_FLOWS：ChatVibe / Dating App 核心业务流程

> 本文档用于把 PRD、服务端架构、导师示例方案中的需求，整理成后端开发前必须理解的业务闭环。
>
> 本文档不写代码，不展开类设计，不替代接口文档。它只解决一个问题：每条核心业务从用户操作开始，到服务协作、数据变化、缓存变化、外部依赖、异常兜底，完整链路是什么。

---

## 0. 阅读方式

后续开发时，不建议按“先写 user-service、再写 match-service、再写 im-service”的方式推进。更好的方式是按业务闭环推进：

1. 先理解用户在 App 上做了什么。
2. 再看 mobile-gateway 如何接收请求并转发内部 gRPC。
3. 再看哪个服务是主服务，哪些服务是协作服务。
4. 再看数据最终落在哪些 PostgreSQL 表里。
5. 再看 Redis 只是做缓存、队列、配额、锁，还是临时状态。
6. 最后识别这条链路的技术难点、幂等点和面试表达点。

本文档中的服务简称：

| 简称 | 服务 |
|---|---|
| GW | mobile-gateway |
| USER | user-service |
| MATCH | match-service |
| IM | im-service |
| POST | post-service |
| PAY | payment-service |
| AI | ai-chat |
| OIM | OpenIM Server |
| LK | LiveKit |

核心原则：

- App 对业务接口只访问 GW。
- 服务之间默认走 gRPC。
- 各服务只能访问自己的 PostgreSQL 表、Redis key、对象存储前缀。
- OpenIM / LiveKit 只能由 IM 封装。
- AI 只提供 Agent 能力，不直接决定支付、匹配、扣费等业务状态。

## 1. 注册登录流程

### 1.1 业务目标

让用户可以通过手机号、第三方授权或设备匿名方式快速进入 App。新用户登录后生成用户占位档案，签发 access token / refresh token，并尽量完成 IM 用户注册和新用户金币奖励。

PRD 侧重点：

- 快速登录优先。
- 支持第三方授权登录。
- 支持手机号登录。
- 注册后填写昵称、性别、年龄、头像。
- 注册完成送 60 金币。

### 1.2 主流程

```text
用户打开 App
  ↓
选择手机号 / 第三方 / 设备登录
  ↓
GW 接收登录请求
  ↓
GW 调 USER：ResolveOrCreateByPhone / ThirdParty / Device
  ↓
USER 判断账号是否已存在
  ├─ 已存在：返回 userId、pending 状态，更新 last_open_at
  └─ 不存在：创建 user_info 占位档案 + 登录绑定记录
  ↓
GW 调 USER：CheckBan
  ↓
GW 写 auth_device、auth_refresh_token
  ↓
GW 签发 access token + refresh token
  ↓
如果是新用户：
  ├─ GW 调 IM：registerImUser，失败不阻塞登录
  └─ GW 调 PAY：AddCoins，发放注册奖励 60 金币
  ↓
App 拿到 token、userId、pending、imToken 获取入口
```

### 1.3 涉及服务

| 服务 | 职责 |
|---|---|
| GW | 对外登录入口；验证码校验；JWT 签发；refresh token 管理；设备登记；调用 USER / IM / PAY |
| USER | 创建或解析用户身份；维护 phone / third_party / device 绑定；检查封禁；创建 user_info 占位档案 |
| IM | 注册 OpenIM 用户，保证后续可以拿 IM token 和收发消息 |
| PAY | 发放新用户注册金币奖励，写金币账户和金币流水 |
| Redis | 验证码、短信冷却、JWT 黑名单、注册锁、封禁缓存 |
| PostgreSQL | 用户身份、设备、refresh token、金币账户、金币流水 |
| OpenIM | 底层 IM 用户体系 |

### 1.4 关键数据变化

| 服务 | 表 | 数据变化 |
|---|---|---|
| GW | `auth_device` | 记录用户设备指纹，唯一索引防止同一用户同一设备重复登记 |
| GW | `auth_refresh_token` | 存 refresh token 的 SHA-256 hash，支持轮换、撤销和 reuse detection |
| USER | `user_info` | 新用户插入 pending=true 的占位档案；老用户更新 last_open_at |
| USER | `user_login_phone` | 手机号登录绑定记录 |
| USER | `user_third_party_registration` | 第三方登录绑定记录 |
| USER | `user_device_registration` | 设备匿名登录绑定记录 |
| PAY | `coin_accounts` | 新用户创建金币账户或更新免费金币余额 |
| PAY | `coin_ledger` | 写入注册奖励流水，reason 可标记为 REGISTER_REWARD |

### 1.5 Redis Key

| Key | 用途 |
|---|---|
| `gateway:auth:sms:code:{phoneE164}` | 短信验证码，TTL 5 分钟 |
| `gateway:auth:sms:cooldown:{phoneE164}` | 发送验证码冷却，TTL 60 秒 |
| `gateway:auth:blacklist:{jti}` | access token 黑名单，登出或强制下线使用 |
| `lock:user:register:phone:{phoneE164}` | 手机号注册防重复 |
| `lock:user:register:thirdparty:{platform}:{thirdPartyUserId}` | 第三方登录注册防重复 |
| `lock:user:register:device:{platform}:{deviceId}` | 设备登录注册防重复 |
| `user:ban:status:{userId}` | 用户封禁状态短缓存 |

### 1.6 技术难点

1. **注册幂等**：同一手机号、第三方账号、设备 ID 并发登录时，不能创建多个用户。USER 需要用唯一索引 + 分布式锁 + 事务兜底。
2. **refresh token 安全**：refresh token 不能明文入库，只存 hash；每次刷新都要轮换，旧 refresh 再次提交要触发 reuse detection。
3. **IM 注册失败兜底**：OpenIM 注册失败不应阻断登录，后续 getImToken 时可以 lazy-register。
4. **新用户奖励幂等**：注册送 60 金币不能重复发放，PAY 应用 `idempotency_key = register_reward:{userId}` 或等价方案兜底。
5. **服务边界**：GW 可以编排 USER / IM / PAY，但不能直接写 USER 或 PAY 的业务表。

### 1.7 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | 手机号 mock 验证码登录、设备登录、JWT、refresh token、USER 创建占位档案、IM 注册兜底、新用户金币奖励 |
| 后续扩展 | Google / Apple / Facebook 真校验、活体检测、风控封禁、登录异常告警、多设备管理 |

## 2. 用户资料完善流程

### 2.1 业务目标

用户首次登录后需要完成基础资料，平台才能进入推荐和匹配。资料完善既是产品 onboarding，也是推荐召回、AI 分析和后续 Feed 推荐的数据基础。

PRD 侧重点：

- 昵称、性别、年龄、头像是注册后关键字段。
- 资料完善通过一次性任务发金币。
- 基本信息任务奖励 60 金币。
- 相册九宫格完善任务奖励 120 金币。
- 支持 Tags、Location、Bio、职业、身高、体重、教育背景、MBTI。

### 2.2 主流程

```text
App 判断 pending=true
  ↓
用户进入资料完善页
  ↓
填写昵称、性别、生日/年龄、城市、Bio、职业、身高、体重、教育、MBTI、兴趣标签
  ↓
GW 调 USER：UpsertOnboarding / UpdateProfile / ReplaceUserInterests
  ↓
USER 校验必填字段和不可变字段
  ↓
USER 事务写 user_info + user_interest
  ↓
USER 将 pending=false
  ↓
USER 删除 profile 相关缓存
  ↓
如果满足任务奖励条件：GW 或 USER 触发 PAY 发放任务金币
  ↓
App 进入首页推荐流
```

### 2.3 涉及服务

| 服务 | 职责 |
|---|---|
| GW | 资料接口入口；从 JWT 解析 callerUserId；把 REST 参数转换成 USER gRPC 请求 |
| USER | 用户资料主数据维护；兴趣标签维护；城市字典校验；缓存失效 |
| PAY | 发放资料完善任务奖励 |
| MATCH | 后续推荐召回会读取 USER 的用户画像数据，但不参与资料写入 |

### 2.4 关键数据变化

| 服务 | 表 | 数据变化 |
|---|---|---|
| USER | `user_info` | 更新 nickname、gender、birthday、age、city_id、lat、lng、beauty_score、race、bio、occupation、height、weight、education、mbti、pending |
| USER | `user_interest` | 全量替换用户兴趣标签 |
| USER | `geo_city` | 只读城市字典，作为 location 的标准化来源 |
| PAY | `coin_ledger` | 写入资料完善任务奖励流水 |

### 2.5 Redis Key

| Key | 用途 |
|---|---|
| `user:profile:{userId}` | 用户基础档案缓存，写资料后删除 |
| `user:profile:big:{userId}` | 用户聚合档案缓存，写资料后删除 |
| `user:interest:{userId}` | 兴趣标签缓存，替换兴趣后删除 |
| `match:pref:{userId}` | D1 推荐偏好画像，资料变化后后续可考虑失效或下次重算 |

### 2.6 技术难点

1. **资料字段的可变与不可变**：性别、生日这类影响推荐和身份的字段，首次 onboarding 后是否允许修改要明确；日常编辑不能随意改。
2. **兴趣标签全量替换**：ReplaceUserInterests 应在事务内先删后插，并清理缓存，避免半更新。
3. **任务奖励幂等**：基本资料奖励和相册奖励必须只能领取一次，不能因为重复提交资料反复加金币。
4. **推荐数据依赖**：MATCH 不应直接写用户资料，只能通过 USER 的 gRPC 读取资料。
5. **数据质量**：城市、年龄、性别、颜值分、人种等字段会影响召回，不能只把资料当普通表单处理。

### 2.7 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | onboarding、基础资料更新、兴趣标签更新、pending 状态、缓存删除、基本资料奖励 |
| 后续扩展 | 资料审核、资料修改次数限制、地理位置自动解析、相册九宫格任务、资料完整度评分 |

## 3. 头像上传与 AI 分析流程

### 3.1 业务目标

用户上传头像或资料照后，系统需要保存图片对象，并通过 AI 判断是否为真人、分析头像质量、计算颜值分，为推荐排序和平台风控提供依据。

PRD 侧重点：

- 头像上传后异步 AI 识别是否真人。
- 计算颜值分。
- 用户资料和相册会影响推荐、数字人构造和用户展示。

### 3.2 主流程

```text
用户选择头像
  ↓
App 调 GW：申请上传凭证
  ↓
GW 调 USER：PresignAvatarUpload
  ↓
USER 校验文件类型、大小、object key 前缀
  ↓
USER 调 MinIO 生成 5 分钟 presigned PUT URL
  ↓
App 直传 MinIO
  ↓
App 调 GW：ConfirmAvatarUpload，提交 object_key
  ↓
GW 调 USER：ConfirmAvatarUpload
  ↓
USER headObject 校验文件存在、大小合法、前缀合法
  ↓
USER 更新 user_info.custom_avatar
  ↓
USER 删除用户资料缓存
  ↓
USER 或 GW 触发 AI：AnalyzeProfilePhoto / ScoreFace
  ↓
AI 返回真人识别、图片描述、颜值分、资料照建议
  ↓
USER 更新 beauty_score、avatar_analysis、审核状态等字段
```

### 3.3 涉及服务

| 服务 | 职责 |
|---|---|
| GW | 上传接口入口；鉴权；把请求转给 USER |
| USER | 生成上传凭证；确认对象存在；维护头像 object_key；保存 AI 分析结果 |
| AI | VisionAgent 执行图片理解、颜值评分、资料照分析 |
| MinIO | 存储头像、相册、Post 图片等对象文件 |
| Redis | 用户资料缓存失效 |

### 3.4 关键数据变化

| 服务 | 表 / 对象 | 数据变化 |
|---|---|---|
| MinIO | `avatar/{userId}/...` | 存储用户上传的头像原图或处理后图片 |
| USER | `user_info.custom_avatar` | 保存 originalKey、minKey、midKey、width、height 等 object_key，不保存永久 URL |
| USER | `user_info.beauty_score` | 保存 AI 颜值评分，用于推荐排序 |
| USER | `user_info.regulation_status` | 可用于保存真人识别、审核中、审核失败等状态 |

### 3.5 Redis Key

| Key | 用途 |
|---|---|
| `user:profile:{userId}` | 头像更新后删除 |
| `user:profile:big:{userId}` | 头像更新后删除 |
| `match:feed:{userId}` | 一般不立即删除；后续推荐队列重建时使用新头像和新颜值分 |

### 3.6 技术难点

1. **上传不经过后端中转**：App 应直传 MinIO，后端只发 presigned URL 和确认 object_key，避免大文件压垮 GW。
2. **只存 object_key**：数据库不存完整 URL，避免域名、bucket、CDN 变化导致历史数据失效。
3. **AI 分析异步化**：头像确认成功后不要长时间阻塞用户；MVP 可同步调用，正式链路建议异步任务或事件驱动。
4. **AI 结果可信度**：模型返回可能失败或格式不稳定，需要兜底；颜值分缺失时推荐排序要能退化。
5. **安全边界**：AI 只给分析结果，是否通过审核、是否更新用户状态，应由 USER 或审核策略决定。

### 3.7 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | presign、直传、confirm、object_key 入库、缓存清理、调用 VisionAgent 评分或预留分析状态 |
| 后续扩展 | 图片裁剪、多尺寸生成、真人检测、涉黄涉暴审核、资料照建议、相册九宫格奖励 |

## 4. D0 / D1 推荐队列流程

### 4.1 业务目标

为首页划卡准备一组可消费的候选卡片。推荐队列不是每次实时从数据库查一页用户，而是提前生成或实时补齐到 Redis List 中，App 拉取时从队列消费。

PRD 侧重点：

- D0 队列是冷启动队列。
- 基于年龄、颜值分、人种等维度分桶。
- D1 队列由定时任务每日生成，前提是前一天有划卡行为。
- 每个队列目标 240 张。

### 4.2 D0 冷启动流程

```text
用户首次进入首页 / 推荐队列为空
  ↓
App 调 GW：GET /api/v1/match/feed
  ↓
GW 调 MATCH：GetTodayFeed
  ↓
MATCH 检查今日 cards 配额
  ↓
MATCH 发现 Redis List 不足
  ↓
MATCH 实时构建 D0 队列
  ├─ 调 USER：ListDhCandidates，召回 DH 数字人
  └─ 调 USER：NearbyUsers，召回 BH 真人
  ↓
MATCH 对 BH / DH 分别排序
  ↓
MATCH 按 bh_ratio 混合 BH / DH
  ↓
MATCH 写入 Redis：match:feed:{userId}
  ↓
MATCH LPOP 消费前 N 张
  ↓
MATCH 二次过滤已划、已拉黑、资料异常用户
  ↓
MATCH 调 USER：BatchGetProfile 拼接卡片展示信息
  ↓
返回 App 首页卡片
```

### 4.3 D1 日更流程

```text
每日定时任务触发
  ↓
MATCH 抢 D1 分布式锁
  ↓
扫描昨天有划卡行为的用户
  ↓
根据近 30 天右划数据计算偏好画像
  ↓
写 Redis：match:pref:{userId}
  ↓
分别召回 BH / DH 候选池
  ↓
按偏好相似度、颜值、距离、活跃度、互相喜欢、新用户加权打分
  ↓
各池取 Top 240
  ↓
根据基础 bh_ratio + 用户个性化偏移进行混合
  ↓
DEL 旧 match:feed:{userId}
  ↓
RPUSH 新推荐队列
```

### 4.4 涉及服务

| 服务 | 职责 |
|---|---|
| MATCH | 推荐队列生成、排序、混排、消费、配额检查、二次过滤 |
| USER | 提供 DH 候选、附近 BH 候选、批量用户资料、DH 城市伪装策略 |
| PAY | 查询订阅档位，用于判断每日卡片数、右划数、Super Hi 赠送次数 |
| Redis | 推荐队列、偏好画像、配额、已划集合、D1 锁 |
| PostgreSQL | 划卡历史、用户资料、匹配关系最终事实源 |

### 4.5 关键数据变化

| 服务 | 表 / Key | 数据变化 |
|---|---|---|
| MATCH | `user_swipe_history` | D1 建模读取近 30 天右划数据 |
| MATCH | `match:feed:{userId}` | 写入推荐队列，元素形如 `targetId:targetType` |
| MATCH | `match:pref:{userId}` | 保存用户推荐偏好画像 |
| MATCH | `match:quota:{userId}:{yyyymmdd}` | 记录今日卡片消耗、右划消耗、Super Hi 消耗 |
| USER | `user_info` | 提供 age、gender、city_id、race、beauty_score、last_open_at 等召回字段 |

### 4.6 技术难点

1. **推荐队列不是最终数据**：Redis 队列可以重建，不能把它当最终事实源。
2. **二次过滤必不可少**：队列生成和消费之间存在时间差，用户可能已经划过、拉黑、被封禁或资料变化。
3. **D0 与 D1 区别**：D0 解决冷启动，D1 利用历史行为做偏好建模。
4. **定时任务防重复**：D1 多实例部署时必须有分布式锁，避免多个实例同时覆盖队列。
5. **跨服务数据获取**：MATCH 不能直接查 USER 表，只能通过 USER gRPC 召回和批量取资料。

### 4.7 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | D0 冷启动队列、GetTodayFeed、Redis List 消费、二次过滤、BatchGetProfile 拼卡 |
| 后续扩展 | D1 偏好建模、个性化 bh_ratio、互相喜欢加权、地理距离衰减、推荐实验参数 |

## 5. 划卡与匹配流程

### 5.1 业务目标

用户对推荐卡片执行左划、右划或 Super Hi。系统要记录用户行为、扣减配额，并在满足规则时创建匹配关系和会话。

PRD 侧重点：

- 首页支持左划、右划。
- 真人之间需要看对方是否也喜欢你，决定是否立即匹配。
- 数字人不能立即匹配，只能延迟匹配。
- Super Hi 收费后可以立即匹配。

### 5.2 普通左划 / 右划流程

```text
用户在首页划卡
  ↓
App 调 GW：POST /api/v1/match/swipe
  ↓
GW 调 MATCH：Swipe(userId, targetId, direction)
  ↓
MATCH 获取 lock:match:swipe:{user}:{target}
  ↓
MATCH 查询 user_swipe_history 是否已存在
  ├─ 已存在：返回上次结果，不重复扣配额
  └─ 不存在：继续
  ↓
MATCH 扣减 cards 配额
  ↓
如果 direction=RIGHT：额外扣减 right_swipe 配额
  ↓
MATCH 写 user_swipe_history
  ↓
MATCH 写 Redis：match:swiped:{userId}
  ↓
根据 target 类型进入匹配判断
  ├─ target=BH：检查对方是否右划过我
  │    ├─ 是：创建 match 关系 + 发送系统消息
  │    └─ 否：仅记录右划行为
  └─ target=DH：进入 DH 延迟匹配流程
```

### 5.3 Super Hi 流程

```text
用户点击 Super Hi
  ↓
App 生成 clientRequestId
  ↓
App 调 GW：POST /api/v1/match/super-hi
  ↓
GW 调 MATCH：SuperHi(userId, targetId, clientRequestId)
  ↓
MATCH 检查订阅赠送 Super Hi 配额
  ├─ 有赠送配额：扣赠送次数
  └─ 无赠送配额：调 PAY ConsumeCoins 扣 100 金币
  ↓
MATCH 立即创建 match 关系
  ↓
MATCH 调 IM：ensureConversation / sendSystemMessage
  ↓
如果 target=DH：触发 DH 开场白
  ↓
返回匹配成功
```

### 5.4 涉及服务

| 服务 | 职责 |
|---|---|
| GW | 划卡接口入口；鉴权；转发 MATCH |
| MATCH | 划卡幂等、配额扣减、历史记录、匹配关系创建、DH 延迟调度、match outbox |
| USER | 提供 target 用户类型、资料、候选信息 |
| PAY | 查询订阅权益；Super Hi 扣金币 |
| IM | 创建会话；发送匹配成功、欢迎消息、DH 开场白 |
| Redis | 配额、已划集合、划卡锁、推荐队列 |

### 5.5 关键数据变化

| 服务 | 表 / Key | 数据变化 |
|---|---|---|
| MATCH | `user_swipe_history` | 写入 LEFT / RIGHT / SUPER_HI 划卡记录，唯一索引防重复 |
| MATCH | `match` | 互相喜欢、Super Hi、DH 延迟完成时创建匹配关系 |
| MATCH | `match_outbox` | 记录 IM 副作用任务，失败后重试 |
| MATCH | `match:quota:{userId}:{yyyymmdd}` | 扣减每日卡片数、右划次数、Super Hi 赠送次数 |
| MATCH | `match:swiped:{userId}` | 记录已划 target，用于推荐队列二次过滤 |
| PAY | `coin_ledger` | Super Hi 扣费流水，幂等键 `superhi:{clientRequestId}` |

### 5.6 技术难点

1. **划卡幂等**：同一 userId + targetId 只能有一条有效划卡记录。重复请求不能重复扣配额、重复创建 match。
2. **配额原子扣减**：每日 cards、right_swipe、super_hi 需要 Redis 原子操作或 Lua 保证并发安全。
3. **匹配创建幂等**：match 表用 `(user_id_low, user_id_high)` 唯一索引兜底，防止双方同时右划创建两条关系。
4. **副作用解耦**：创建 match 后还要创建 IM 会话、发系统消息，这些副作用应通过 outbox 重试，不能因为 IM 短暂失败导致匹配关系丢失。
5. **业务矩阵清晰**：BH 与 BH、BH 与 DH、Super Hi 与普通右划的结果不同，不能写成一坨 if else 后失去可解释性。

### 5.7 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | LEFT / RIGHT、划卡历史、配额、BH 互划立即匹配、match 唯一索引、基础系统消息 |
| 后续扩展 | Super Hi、Like Visit、DH 延迟匹配、match outbox 重试、更多付费权益 |

## 6. DH 延迟匹配流程

### 6.1 业务目标

用户右划数字人 DH 后，不能立刻匹配，否则容易暴露“数字人非真人”的产品体验问题。系统需要模拟真人响应节奏，在 15 秒到 2 分钟之间延迟创建匹配，并可能触发数字人开场白。

### 6.2 主流程

```text
用户右划 DH
  ↓
MATCH 写 user_swipe_history
  ↓
MATCH 判断 target_user_type=DH
  ↓
MATCH 生成延迟时间：15s - 2min
  ↓
MATCH 写入 DH pending 状态或进程内延迟任务
  ↓
延迟时间到达
  ↓
MATCH 再次校验：用户未被封禁、未取消、未重复匹配、target 仍可用
  ↓
MATCH 创建 match 关系
  ↓
MATCH 写 match_outbox：ensureConversation / match_welcome / dh_opening
  ↓
IM 创建会话并发送欢迎消息
  ↓
IM 或 MATCH 触发 AI 生成 DH 开场白
```

### 6.3 涉及服务

| 服务 | 职责 |
|---|---|
| MATCH | DH 延迟任务调度、状态校验、创建 match、outbox 重试 |
| USER | 查询 BH / DH 用户类型和基础资料 |
| IM | 创建会话、发送匹配通知和欢迎消息 |
| AI | 生成 DH 开场白或后续聊天回复 |
| Redis | 延迟任务临时状态、锁、配额、已划集合 |

### 6.4 关键数据变化

| 服务 | 表 / Key | 数据变化 |
|---|---|---|
| MATCH | `user_swipe_history` | 记录用户右划 DH |
| MATCH | `match` | 延迟结束后创建匹配关系 |
| MATCH | `match_outbox` | 记录 IM 副作用任务 |
| Redis | DH pending 相关 key | 保存延迟匹配待执行状态；导师方案中可用进程内 TaskScheduler，正式方案可升级为 Redis ZSet / MQ 延迟消息 |

### 6.5 技术难点

1. **延迟任务可靠性**：进程内 TaskScheduler 简单，但服务重启可能丢任务；正式场景可以升级 Redis ZSet、RocketMQ 延迟消息或 XXL-JOB 补偿扫描。
2. **重复触发**：用户重复右划、接口重试、延迟任务重试都不能重复创建 match。
3. **状态二次校验**：延迟执行时不能假设发起时状态仍有效，必须重新校验用户、target、match 是否仍可创建。
4. **体验节奏**：延迟时间不能固定，避免被用户感知为机器逻辑。
5. **AI 开场白边界**：AI 只生成内容，最终是否发送、以什么身份发送，由 IM 统一处理。

### 6.6 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | 右划 DH 后延迟创建 match、基础欢迎消息、match 唯一索引兜底 |
| 后续扩展 | Redis ZSet 延迟队列、RocketMQ 延迟消息、DH 开场白策略、失败补偿任务、个性化延迟时间 |

## 7. IM 聊天与金币扣费流程

### 7.1 业务目标

匹配成功后用户才能聊天。聊天底层由 OpenIM 负责消息投递，业务层由 IM 处理扣费、反导流、消息存档、AI 路由和系统通知。

PRD 侧重点：

- 匹配成功之后才有 chat。
- 如果是数字人会由 AI 接管。
- 支持文字、图片、GIF、语音、视频。
- 发消息消耗金币，配对前 3 条消息免费。
- 送礼物、语音、视频也可以收费。

### 7.2 发消息前置扣费流程

```text
用户在 App 发送消息
  ↓
App 通过 OpenIM SDK 发给 OIM
  ↓
OIM 触发 beforeSend 回调
  ↓
OIM POST 到 GW：/callback/openim/{cmd}
  ↓
GW 校验回调 IP 白名单，透传 raw payload 给 IM
  ↓
IM 解析 OpenIM 回调事件
  ↓
IM 调 USER：batchGetUserType，判断发送方是 BH 还是 DH
  ↓
如果发送方是 DH：直接放行，不扣费、不反导流
  ↓
如果发送方是 BH：
  ├─ 反导流检测：手机号、WhatsApp、Telegram、Instagram 等
  │    ├─ 命中：reject，消息不发送
  │    └─ 未命中：继续
  ├─ 检查是否属于本 match 的前 3 条免费消息
  │    ├─ 免费额度内：放行，记录免费计数
  │    └─ 免费额度外：调 PAY GetCoins 判断余额
  ├─ 余额不足：reject，提示金币不足
  └─ 余额足够：异步调 PAY ConsumeCoins，放行消息
  ↓
OIM 收到 allow 后投递消息
```

### 7.3 发送后存档与 AI 路由流程

```text
OIM 消息发送成功
  ↓
OIM 触发 afterSend 回调
  ↓
GW 透传到 IM
  ↓
IM 落库 chat_messages
  ↓
IM 判断 route_type
  ├─ BH_BH：只存档，不触发 AI
  ├─ DH_BH：AI 发出的消息，只存档
  └─ BH_DH：触发 AI Chat 回复
```

### 7.4 涉及服务

| 服务 | 职责 |
|---|---|
| OIM | 底层消息连接、投递、回调 |
| GW | OpenIM 回调入口；IP 白名单；raw payload 透传 |
| IM | 回调解析、扣费准入、反导流、消息存档、AI 路由、业务通知 |
| USER | 提供用户类型 BH / DH |
| PAY | 查询金币余额、扣金币、写金币流水 |
| AI | 数字人回复和图片理解 |
| Redis | 在线状态、免费消息计数、扣费幂等辅助、反导流配置缓存 |

### 7.5 关键数据变化

| 服务 | 表 / Key | 数据变化 |
|---|---|---|
| IM | `chat_messages` | 保存 OpenIM 消息记录，含 from_user_id、to_user_id、content、type、route_type、timestamp |
| IM | `user_online_session` | 上下线回调时记录在线时长 |
| Redis | `im:presence:online` | 在线用户 ZSet，由 OpenIM 上下线回调维护 |
| Redis | `im:free_msg:{matchId}:{userId}` | 建议用于记录当前匹配的免费消息使用数，MVP 可简化 |
| PAY | `coin_ledger` | 消息扣费流水，幂等键 `im-msg:{messageId}` |

### 7.6 技术难点

1. **OpenIM 只负责投递，不负责业务语义**：扣费、反导流、AI 路由必须在 IM 完成。
2. **beforeSend 与 afterSend 分工**：beforeSend 决定放行或拒绝；afterSend 做存档和异步 AI，不应阻断用户发消息。
3. **消息扣费幂等**：OpenIM 回调可能重复，PAY 通过 `im-msg:{messageId}` 保证同一消息只扣一次。
4. **前 3 条免费消息**：需要明确计数维度，是每个 match、每个发送方、还是双方共享；建议按 matchId + senderUserId 记录。
5. **反导流 fail-safe**：检测异常时是放行还是拒绝要明确；收费异常一般 fail-close，AI 异常则不影响聊天。
6. **OpenIM admin secret 红线**：只有 IM 能持有 OpenIM admin secret，MATCH / POST / USER 不能直接调用 OpenIM。

### 7.7 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | getImToken、OpenIM 回调、消息存档、BH/DH 路由、基础扣费、金币不足拒绝 |
| 后续扩展 | 前 3 条免费额度、礼物、GIF、语音、视频收费、反导流策略、在线状态统计、消息风控 |

## 8. AI Chat 数字人回复流程

### 8.1 业务目标

当 BH 真人用户给 DH 数字人发送消息后，系统要由 AI 接管 DH 的回复，模拟真实用户对话体验。AI Chat 是 Python Agent 服务，但必须嵌入 IM 业务链路，而不是独立 Demo。

### 8.2 主流程

```text
BH 给 DH 发送 TEXT / IMAGE 消息
  ↓
OIM afterSend 回调进入 IM
  ↓
IM 落 chat_messages
  ↓
IM 判断 route_type = BH_DH
  ↓
如果是 IMAGE：
  ├─ IM 解析 OpenIM PictureElem 获取 image_url
  ├─ IM 调 AI：VisionAgent.Understand
  └─ 将图片描述转换成 [Image] 描述文本
  ↓
IM 调 AI：ChatAgent.Chat
  ├─ thread_id = {fromUserId}:{toUserId}
  ├─ from_user_id = BH
  ├─ to_user_id = DH
  └─ message = 用户文本或图片描述
  ↓
AI 调 USER：BatchGetProfiles，拉 BH / DH 双方资料
  ↓
AI 从 LangGraph checkpointer 读取历史上下文
  ↓
AI 执行意图分类、动态提示词注入、回复生成
  ↓
AI 返回回复文本
  ↓
IM 对回复分句，模拟打字节奏
  ↓
IM 通过 OpenIM REST 以 DH 身份发送消息给 BH
  ↓
OIM 投递消息，后续 afterSend 回调再由 IM 存档
```

### 8.3 涉及服务

| 服务 | 职责 |
|---|---|
| IM | 判断 BH→DH 路由；组织 AI 请求；发送 AI 回复；控制分句和打字节奏 |
| AI | ChatAgent 生成数字人回复；VisionAgent 理解图片；维护 LangGraph 上下文 |
| USER | 提供 BH / DH 用户资料，作为 AI prompt 上下文 |
| OIM | 投递 AI 回复消息 |
| PostgreSQL | chat_messages、LangGraph checkpointer |

### 8.4 关键数据变化

| 服务 | 表 / 存储 | 数据变化 |
|---|---|---|
| IM | `chat_messages` | 保存 BH 原始消息和 DH AI 回复消息 |
| AI | LangGraph checkpointer PostgreSQL | 按 thread_id 保存多轮对话上下文 |
| USER | `user_info` | 只读用户资料，用于 AI 个性化回复 |

### 8.5 技术难点

1. **thread_id 设计**：建议使用 `{bhUserId}:{dhUserId}`，保证同一对用户共享上下文。
2. **AI 不阻塞主链路**：afterSend 触发 AI，AI 失败只记录日志，不影响用户原消息发送。
3. **图片消息处理**：IMAGE 需要先转成文本描述，再交给 ChatAgent，否则 DH 无法理解图片语义。
4. **回复分句与节奏**：AI 直接返回长文本会显得不真实，IM 需要拆句并延迟发送。
5. **上下文压缩**：聊天轮次变多后，LangGraph 需要摘要压缩，避免 token 无限增长。
6. **权限边界**：AI 不能直接扣费、创建 match、绕过 IM 发消息；它只返回内容。

### 8.6 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | BH→DH 文本回复、thread_id 上下文、USER 档案注入、IM 发送 AI 回复 |
| 后续扩展 | 图片理解、意图分类、上下文摘要、多模型路由、熔断降级、LangSmith 观测、数字人个性化人设 |

## 9. Post Feed 发帖 / 点赞 / 评论 / 推荐流程

### 9.1 业务目标

Post Feed 是 Dating App 的内容流，用于增强用户活跃、提供非划卡场景的互动入口，并承载 Super Hi、Like Visit 等付费转化场景。

PRD 侧重点：

- 用户可以发帖、删帖。
- 可以点赞、评论，楼中楼最多 2 层。
- Feed 由全网热门、好友、新帖融合生成。
- 只看异性内容。
- 数字人也可以通过 AI 生产 Post 信息并定时发布。

### 9.2 发帖流程

```text
用户选择文字和图片
  ↓
App 先通过上传接口把图片直传 MinIO，获得 image_key
  ↓
App 调 GW：发布帖子
  ↓
GW 调 POST：CreatePost
  ↓
POST 校验文本、图片数量、图片 key 归属
  ↓
POST 事务写 post、post_image、post_stat
  ↓
POST 写 Redis：post:detail:{postId}
  ↓
POST 将帖子加入 feed:cold_start:pool:{gender}
  ↓
POST 异步 fanout 到好友时间线 user:timeline:{followerId}
  ↓
返回 postId
```

### 9.3 点赞 / 取消点赞流程

```text
用户点赞或取消点赞
  ↓
GW 调 POST：ActionLike
  ↓
POST upsert post_like，保证幂等
  ↓
如果状态真实发生变化：
  ├─ Redis 计数增量 +1 / -1
  ├─ 写 updated_posts_set
  └─ 返回最新展示计数 = DB 基准值 + Redis 增量
  ↓
LikeFlushJob 定时刷盘
  ↓
POST 批量把 Redis 增量回写 post_stat
```

### 9.4 评论流程

```text
用户发表评论
  ↓
GW 调 POST：CreateComment
  ↓
POST 校验帖子存在、评论层级不超过 2 层
  ↓
POST 写 post_comment
  ↓
POST 写 Redis：post:comments:{postId} 最新评论窗口
  ↓
POST 评论计数增量 +1
  ↓
返回评论内容
```

### 9.5 推荐 Feed 流程

```text
用户进入 Post Feed
  ↓
GW 调 POST：GetRecommendFeed
  ↓
POST 根据用户性别确定目标内容池：只看异性
  ↓
POST 从三路池取候选
  ├─ feed:pool:recommend:{targetGender}：全网热门池
  ├─ user:timeline:{userId}：好友时间线
  └─ feed:cold_start:pool:{targetGender}：新帖冷启动池
  ↓
POST 过滤已读、已删除、作者异常、同性内容
  ↓
POST 按比例混合三路内容，可强插冷启动内容
  ↓
POST 批量查 post、post_image、post_stat、like 状态
  ↓
POST 合并 Redis 计数增量
  ↓
POST 写 user:read:bloom:{userId}
  ↓
返回 Feed 列表
```

### 9.6 涉及服务

| 服务 | 职责 |
|---|---|
| POST | 发帖、删帖、点赞、评论、Feed 三路融合、计数写合并 |
| USER | 后续用于补充作者资料、性别、头像、用户状态 |
| MinIO | 存储帖子图片 |
| Redis | 帖子详情缓存、计数增量、评论窗口、Feed 池、用户时间线、已读布隆过滤 |
| PostgreSQL | Post 最终事实源 |

### 9.7 关键数据变化

| 服务 | 表 / Key | 数据变化 |
|---|---|---|
| POST | `post` | 帖子主表，记录作者、内容、状态 |
| POST | `post_image` | 帖子图片列表，最多 9 张 |
| POST | `post_stat` | DB 计数基准值 |
| POST | `post_like` | 点赞幂等记录 |
| POST | `post_comment` | 评论记录，预留楼中楼字段 |
| Redis | `post:stat:incr:{postId}:likes` | 点赞计数增量 |
| Redis | `post:stat:incr:{postId}:comments` | 评论计数增量 |
| Redis | `feed:pool:recommend:{male,female}` | 推荐池 |
| Redis | `feed:cold_start:pool:{male,female}` | 新帖冷启动池 |
| Redis | `user:timeline:{userId}` | 好友时间线 |
| Redis | `user:read:bloom:{userId}` | 已读过滤 |

### 9.8 技术难点

1. **计数写合并**：点赞、评论高频更新不能每次直接 UPDATE `post_stat`，应先 Redis 累加，再定时批量刷盘。
2. **点赞幂等**：同一用户对同一帖子只能处于点赞或取消状态，不能重复 +1。
3. **Feed 三路融合**：热门池、好友时间线、新帖冷启动池的目标不同，不能简单按时间倒序。
4. **只看异性**：Dating App 的 Feed 推荐必须带性别分桶，这是业务规则，不是普通社区 Feed。
5. **缓存一致性**：帖子删除后需要处理详情缓存、推荐池、评论窗口、时间线中的旧数据。
6. **POST 边界**：POST 可以做内容互动和 Feed 推荐，但不能直接创建 match 或扣金币；Super Hi 入口可以在 Feed 出现，但最终仍应调用 MATCH / PAY。

### 9.9 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | 发帖、删帖、点赞、评论、帖子详情、基础推荐 Feed、Redis 计数增量 |
| 后续扩展 | 热门池刷新、好友写扩散、冷启动强插、布隆已读过滤、数字人自动发帖、Feed 内 Super Hi 转化 |

## 10. 支付与金币流水流程

### 10.1 业务目标

金币系统支撑聊天扣费、Super Hi、Like Visit、礼物、语音视频等付费行为；订阅系统支撑更高配额、去模糊、折扣和每日 Say Hi。支付系统要保证账户余额准确、流水可追溯、支付回调幂等。

PRD 侧重点：

- 注册、资料完善、签到等可发免费金币。
- 系统派发金币和付费购买金币是不同账目。
- 发消息消耗金币，文档中提到 6 金币。
- Visit 解锁 20 金币，Super Hi 100 金币。
- Like 解锁 20 金币，Like 配对 20 金币。
- 周度 / 月度 / 年度订阅影响右划、卡片、Say Hi、金币折扣。

### 10.2 购买金币流程

```text
用户选择金币商品
  ↓
App 调 GW：CreateOrder
  ↓
GW 调 PAY：CreateOrder
  ↓
PAY 创建本地 payment_orders，状态 INIT
  ↓
PAY 调 PayPal 创建外部订单
  ↓
PAY 返回 checkout_url / ext_order_id
  ↓
用户在 PayPal 完成支付
  ↓
PayPal 回调 PAY Webhook
  ↓
PAY 验签
  ↓
PAY 根据 ext_order_id / order_id 查本地订单
  ↓
PAY capture 或确认支付成功
  ↓
PAY 更新 payment_orders=PAID
  ↓
PAY 调 AddPaidCoins
  ↓
PAY 更新 coin_accounts.paid_balance
  ↓
PAY 写 coin_ledger INCOME 流水
```

### 10.3 消费金币流程

```text
上游服务发起消费
  ├─ IM：消息扣费，idempotency_key = im-msg:{messageId}
  ├─ MATCH：Super Hi，idempotency_key = superhi:{clientRequestId}
  ├─ MATCH：Like / Visit 解锁或促成匹配
  └─ IM：礼物、语音、视频等后续消费
  ↓
PAY 查询 coin_ledger 是否已有相同 idempotency_key
  ├─ 已存在：直接返回历史结果
  └─ 不存在：继续
  ↓
PAY 查询 coin_accounts
  ↓
余额不足：返回错误
  ↓
余额足够：优先扣免费金币 balance，再扣付费金币 paid_balance
  ↓
PAY 乐观锁更新 coin_accounts.version
  ↓
PAY 插入 coin_ledger EXPENSE 流水
  ↓
返回 balance_after
```

### 10.4 订阅权益流程

```text
用户购买周度 / 月度 / 年度订阅
  ↓
PAY 支付成功后激活 user_subscription
  ↓
MATCH 查询 GetSubscription
  ↓
MATCH 根据 tier 计算每日右划、每日卡片、Super Hi 赠送次数
  ↓
POST / MATCH / IM 后续可根据订阅权益开放去模糊、Say Hi、折扣等能力
```

### 10.5 涉及服务

| 服务 | 职责 |
|---|---|
| PAY | 金币账户、金币流水、支付订单、订阅权益、支付回调、幂等消费 |
| GW | 对 App 暴露支付订单和验单入口；转发 PAY |
| MATCH | 消耗金币购买 Super Hi、Like / Visit 解锁；查询订阅配额 |
| IM | 聊天、礼物、语音、视频扣费 |
| PayPal | 第三方支付渠道 |
| Redis | 订阅查询可短缓存；支付链路原则上以 PostgreSQL 为准 |

### 10.6 关键数据变化

| 服务 | 表 | 数据变化 |
|---|---|---|
| PAY | `coin_accounts` | 维护免费金币 balance、付费金币 paid_balance、乐观锁 version |
| PAY | `coin_ledger` | append-only 金币流水，记录收入、支出、余额快照、reason、extra、idempotency_key |
| PAY | `payment_orders` | 记录订单状态 INIT / PAID / FAILED / REFUNDED 等 |
| PAY | `user_subscription` | 记录订阅档位、过期时间、来源 |

### 10.7 技术难点

1. **免费金币与付费金币分账**：系统派发和用户购买必须分开，消费时优先扣免费金币，再扣付费金币。
2. **金币流水 append-only**：不能只更新余额，必须有可追溯流水，方便对账、退款、风控和面试表达。
3. **消费幂等**：IM 回调、Super Hi 请求、支付回调都可能重复，PAY 必须以 idempotency_key 做最终兜底。
4. **支付回调可信性**：PayPal Webhook 必须验签，不能相信客户端“我已支付”。
5. **订单与发币一致性**：订单 PAID 和 AddPaidCoins 之间要有事务或补偿机制，避免付了钱但金币未到账。
6. **上游服务不能自己扣余额**：MATCH / IM 只能调用 PAY，不能直接改 coin_accounts。

### 10.8 MVP 与扩展

| 类型 | 内容 |
|---|---|
| MVP 必做 | coin_accounts、coin_ledger、ConsumeCoins、AddCoins、Super Hi 扣费、IM 扣费、订阅查询 mock 或基础实现 |
| 后续扩展 | PayPal 真支付、Webhook 验签、首充翻倍、签到奖励、Like Visit、礼物、语音视频扣费、退款、提现 |

## 11. 十条业务流的主线关系

这 10 条流程不是彼此独立的模块，而是一个递进闭环：

```text
注册登录
  ↓
资料完善 + 头像 AI 分析
  ↓
生成 D0 / D1 推荐队列
  ↓
用户划卡
  ↓
匹配成功 / DH 延迟匹配
  ↓
进入 IM 聊天
  ↓
聊天扣金币 / AI 数字人回复
  ↓
用户在 Post Feed 中继续互动
  ↓
Super Hi / Like Visit / 支付购买金币 / 订阅
  ↓
金币流水和用户行为继续反哺推荐与运营
```

从学习角度看，这条主线可以拆成 5 类能力：

| 能力 | 对应流程 |
|---|---|
| 账号与用户画像 | 注册登录、资料完善、头像 AI 分析 |
| 推荐与匹配 | D0 / D1 队列、划卡、DH 延迟匹配 |
| IM 与实时互动 | OpenIM 回调、聊天扣费、AI Chat 回复 |
| 内容与增长 | Post Feed、点赞、评论、推荐池 |
| 商业化闭环 | 金币账户、金币流水、支付、订阅、Super Hi、Like Visit |

## 12. 面试表达提炼

后续你讲这个项目时，不要说“我做了几个 CRUD 服务”，而要按业务闭环表达。

### 12.1 可以这样讲项目整体

ChatVibe 是一个 Dating App 后端项目，我不是按表做 CRUD，而是按业务域拆成 user、match、im、post、payment、ai-chat 几个服务。移动端只访问 mobile-gateway，内部服务之间通过 gRPC 调用，服务发现和配置走 Nacos，数据持久化用 PostgreSQL，Redis 负责推荐队列、配额、缓存、锁和计数加速，OpenIM 只作为底层 IM 引擎，由 im-service 统一封装。

### 12.2 可以这样讲推荐与匹配

首页推荐不是每次实时查数据库，而是 MATCH 提前或实时构建 Redis 推荐队列。D0 用于冷启动，D1 根据用户近 30 天右划行为做偏好建模。用户划卡时先做配额扣减和幂等检查，真人之间互相右划才立即匹配，数字人右划要延迟匹配，Super Hi 则通过订阅赠送或金币扣费直接匹配。

### 12.3 可以这样讲 IM 与 AI

聊天底层用 OpenIM，但业务逻辑不放在 OpenIM 里。OpenIM 的 beforeSend 回调进入 im-service 做反导流、金币余额准入和扣费幂等，afterSend 回调用来存档并判断是否触发 AI。如果是真人发给数字人，im-service 会调用 Python ai-chat，ai-chat 通过 LangGraph 维护上下文，再由 im-service 把数字人回复通过 OpenIM 发回去。

### 12.4 可以这样讲金币流水

金币账户不是简单一个 balance 字段。系统区分免费金币和付费金币，消费时优先扣免费金币，再扣付费金币。所有收入和支出都写 append-only 流水，并用 idempotency_key 防止消息回调、Super Hi、支付回调重复导致重复扣费或重复发币。
