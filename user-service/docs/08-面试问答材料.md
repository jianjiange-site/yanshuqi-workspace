# user-service 面试问答材料

> **阅读顺序**：8 / 9

每题 3～6 句话，可直接口述。结合 ChatVibe / Dating App 场景。

---

## 职责与边界

**Q1. user-service 在整个系统里负责什么？**  
它负责用户注册、登录密码校验、账号状态、资料维护、头像/相册 object key 绑定，以及给 match/gateway 用的批量资料读和可用性判断。JWT、REST 网关、推荐排序、IM、支付都不在这里做。

**Q2. 为什么登录校验和发 token 要拆开？**  
VerifyLogin 只验证凭证和账号是否可用，返回 user_id 等事实。Token 由 mobile-gateway 统一签发，方便多端刷新、踢下线，也和 user-service 的「资料服务」定位一致。

**Q3. 下游服务能不能直连 user_center 库？**  
不能。数据库是 user-service 私有资产，下游只走 gRPC。否则 schema 变更、缓存策略、头像审核规则都无法统一，微服务边界就破了。

**Q4. user-service 为什么不做图片上传？**  
上传走客户端 + 对象存储，user-service 只绑定 object_key 并记审核状态。这样存储扩容、CDN、presigned URL 都不耦合在用户服务里。

**Q5. 为什么不做推荐算法？**  
推荐排序属于 match-service 的领域，需要滑动、地理位置、偏好等数据。user-service 只提供「用户是谁、资料快照、是否可用」这类事实数据。

## 注册与事务

**Q6. 注册为什么要写四张表？**  
users 主账号、user_auth_identities 凭证、user_profiles 资料壳、user_settings 默认设置，缺一不可。四表在同一事务里提交，避免只建了账号却没有资料或设置。

**Q7. 注册失败会怎样？**  
本地事务回滚，四表都不会留下半拉子数据。若是手机号/邮箱已存在，抛 IDENTITY_ALREADY_EXISTS，映射 gRPC ALREADY_EXISTS。

**Q8. 注册接口幂等吗？**  
同一 identity 重复注册不幂等，靠 identity_hash 唯一约束拦截。客户端应引导用户去登录，而不是反复 Register。

**Q9. 注册时 profile_status 初始值是什么？**  
一般为资料未完成状态（如 INIT），随 UpdateProfile、BindUserPhoto 由 ProfileStatusResolver 推进到 PROFILE_DONE、PHOTO_DONE 等。

**Q10. user_settings 注册时写什么？**  
写默认记录，例如 discoverable 等开关，为后续「是否出现在发现页」预留，本阶段 RPC 未暴露修改接口。

## 密码与 identity

**Q11. 密码怎么存？**  
明文只在请求里短暂存在，入库前用 BCrypt 哈希，存在 user_auth_identities.password_hash。日志和响应都不带密码字段。

**Q12. identity_hash 是什么？**  
手机号或邮箱归一化后做 SHA-256，用于唯一索引和登录查询。库里不依赖明文 identity 做等值查找，降低泄露面。

**Q13. 为什么日志不能打手机号？**  
合规和运维安全：日志常进 ELK，明文手机号属于 PII。项目用脱敏 identity_value 展示，查重和登录用 hash。

**Q14. 同一用户能绑多种登录方式吗？**  
表结构支持多 identity_type，本阶段 Register 一次创建一种。扩展时仍用 identity_hash 防重复。

**Q15. PASSWORD_INVALID 和 IDENTITY_NOT_FOUND 为什么都是 UNAUTHENTICATED？**  
对外不区分「用户不存在」和「密码错误」，防止撞库枚举账号。客户端统一提示「账号或密码错误」。

## 登录与账号状态

**Q16. 登录除了验密码还做什么？**  
校验 account_status 是否 DISABLED/BANNED/DELETED；upsert user_devices；更新 users.last_login_at。不签发 JWT。

**Q17. USER_BANNED 时 gRPC 返回什么？**  
UserBizException + PERMISSION_DENIED，message 为 errorCode 字符串。gateway 应拒绝后续业务并提示用户。

**Q18. token_version 有什么用？**  
存在 users 表，给 gateway 踢下线或「全端登出」时递增，使旧 JWT 失效。user-service 本阶段不消费 token，只维护字段。

**Q19. 删除用户 account_status=DELETED 还能登录吗？**  
不能，VerifyLogin 会 PERMISSION_DENIED。下游批量接口里 available 也会为 false。

**Q20. last_login_at 谁更新？**  
VerifyLogin 成功后在 UserAuthServiceImpl 里更新 users 表，用于运营统计和风控，不暴露给批量外显接口。

## 设备

**Q21. user_devices 为什么在登录时 upsert？**  
同一 user_id + device_fingerprint 不重复插行，只更新 last_seen_at 和 push_token_hash。多设备登录可追踪，推送可路由。

**Q22. device_fingerprint 会返回给别的服务吗？**  
批量资料接口不返回设备信息。设备表是 user-service 内部能力，避免隐私扩散。

**Q23. push_token_hash 为什么存 hash？**  
推送 token 也是敏感凭证，hash 后入库，和 password 一样降低库泄露风险。

## 资料与 profile

**Q24. profile_score 怎么算？**  
ProfileCompletionCalculator 根据昵称、性别、生日、地区、bio、兴趣等字段加权，UpdateProfile 后写回 user_profiles。

**Q25. profile_completed 和 profile_score 区别？**  
score 是数值完整度；completed 常表示是否达到产品定义的「最低可推荐门槛」，两者一起驱动 profile_status。

**Q26. profile_status 状态机大致怎样？**  
从 INIT 随资料填写到 PROFILE_DONE，绑头像后到 PHOTO_DONE 等。users.profile_status 与资料/照片 Service 协同更新。

**Q27. 为什么资料和 users 分表？**  
账号生命周期和展示字段变更频率不同；批量读可只拉 profiles + 少量 users 字段；扩展审核字段时不污染 auth 表。

**Q28. UpdateProfile 后为什么要删 Redis？**  
basic/profile/status 三个 key 可能缓存了旧昵称、头像 key 或可用性快照。写库成功后删缓存，下次批量读回源。

## 照片与 object_key

**Q29. object_key 格式有什么要求？**  
PhotoObjectKeyValidator 校验前缀归属（如含 user_id 路径），防止用户绑定别人的图。非法抛 PHOTO_OBJECT_KEY_INVALID。

**Q30. 头像为什么只允许一张 enabled？**  
绑新头像前 disableCurrentAvatar，保证当前头像唯一；历史记录保留 enabled=0，便于审计和回滚。

**Q31. 相册 sort_order 干什么用？**  
ALBUM 类型多图按 sort_order 排序展示，上限 20 张。ListUserPhotos 按类型和顺序返回。

**Q32. PENDING 头像为什么批量接口不外显？**  
未审核通过不能出现在推荐卡、匹配列表。BatchGetBasicProfiles 只取 APPROVED 的 enabled 头像；本人 GetSelfProfile 可见 PENDING。

**Q33. avatar_key 冗余在 user_profiles 的原因？**  
本人中心读一次 profile 就能拿当前 key，不必每次聚合 user_photos。外显批量仍走 photos 表审核规则。

**Q34. BindUserPhoto 会改 profile_status 吗？**  
绑头像类型且成功后，会推进到 PHOTO_DONE 并删 Redis，与资料完成度逻辑一致。

## Redis 与缓存

**Q35. 三个 Redis key 分别缓存什么？**  
basic 缓存 BatchGetBasicProfiles 的 VO；profile 缓存推荐用更丰富字段；status 缓存 CheckUserAvailable 结果。TTL 均为 600 秒。

**Q36. cache-aside 流程？**  
先 multiGet，命中直接用；miss 的 user_id 批量 IN 查 DB；Service 合并后 set 回 Redis。写路径 UpdateProfile/BindUserPhoto 删 key。

**Q37. Redis get 失败怎么办？**  
CacheSafeExecutor 捕获异常打 warn，当作全部 miss，继续读 DB，接口仍成功。不能因为缓存挂了阻断业务。

**Q38. 反序列化失败为什么删 key？**  
说明缓存里 JSON 与当前 VO 版本不一致或数据损坏。删掉坏 key 强制回源，避免永远读错数据。

**Q39. 为什么 TTL 设 600 秒？**  
平衡命中率和新鲜度：资料不会秒级变，10 分钟可接受；写路径会主动删缓存，TTL 是兜底过期。

## 异常、日志与分层

**Q40. UserBizException 和普通 Exception 区别？**  
业务异常带 UserErrorCode，Grpc Advice 映射成标准 Status。未知异常统一 INTERNAL，不把堆栈给客户端。

**Q41. ALREADY_EXISTS 和 ABORTED 分别什么时候用？**  
重复注册用 ALREADY_EXISTS；并发更新冲突如乐观锁失败用 ABORTED（USER_CONCURRENT_CONFLICT）。

**Q42. 慢调用日志阈值多少？**  
默认 500ms，超过打 warn，带 method、costMs、userId 等，便于排查 DB 或 Redis 慢。

**Q43. 哪些字段禁止打日志？**  
password、identity 明文、hash、token、device_fingerprint、push_token、AK/SK 等，用 LogMaskUtil 脱敏。

**Q44. Mapper 为什么禁止 JOIN？**  
单表职责清晰，利于分库分表演进；批量外显规则（审核头像）在 Service 聚合更灵活，不绑死在 SQL。

**Q45. Service 和 Manager 怎么分工？**  
Manager 单表 CRUD 和单表规则；Service 跨表编排（注册、批量合并、可用性判断）。gRPC 层不写业务。

## 下游接入

**Q46. match-service 该怎么拿用户头像？**  
调 BatchGetBasicProfiles 或 BatchGetRecommendProfiles，用返回的 avatar_key，由 gateway 拼 CDN URL。不要查库。

**Q47. 批量接口一次最多多少 user_id？**  
有上限（如 USER_BATCH_SIZE_EXCEEDED），防止一次拉全站用户。具体看 proto 与校验常量。

**Q48. CheckUserAvailable 和 BatchGet 里 available 关系？**  
语义一致：账号非 BANNED/DELETED/DISABLED 等即可用。高频过滤可单独调 CheckUserAvailable 并缓存 status key。

**Q49. 用户被 BANNED 下游如何感知？**  
登录 VerifyLogin 直接 PERMISSION_DENIED；已登录用户靠 token_version 或定期 CheckUserAvailable / 批量读 available=false。

**Q50. 为什么推荐列表不自己算分？**  
user-service 的 BatchGetRecommendProfiles 只是「推荐展示用资料快照」，排序权重、距离、活跃度在 match-service 算，职责分离。

## 综合

**Q51. 如果让你用三句话介绍这个模块？**  
user-service 是 dating 产品的 gRPC 用户中心，管注册登录校验、资料和照片 key。读多用 Redis cache-aside，写后删缓存。不做 JWT、网关 REST 和推荐算法。

**Q52. 这个模块最大的技术亮点？**  
边界清晰 + 安全默认（hash/BCrypt/脱敏）+ 可降级缓存 + 统一 gRPC 错误码，且每阶段有可执行验收脚本。

**Q53. 如果 Redis 和 DB 数据不一致怎么办？**  
以 DB 为准；写操作会删缓存；TTL 10 分钟兜底。极端情况可运维删 key 或等过期，不做双写一致性强耦合。

**Q54. 未来扩展 OAuth 放哪？**  
仍在 user-service 增 identity 类型和 Register 变体，或 gateway 编排后调内部接口；仍不破坏「凭证在 auth 表、主键 user_id 贯穿」模型。

**Q55. 为什么不用分布式事务注册四表？**  
四表同库同 schema，Spring 本地事务足够。跨服务才需要 Saga/消息，当前没有跨服务写。

## USER-09 Swagger 适配

**Q56. 你怎么根据 Swagger 反推 user-service 改造范围？**  
先看 REST 路径属于哪域：Auth/Profile/Upload/HomeCard 且需要 user 事实数据的，在 user-service 补 gRPC；JWT、短信发送、OAuth verify、match 聚合则排除。对照 DIFF 文档标「需要支撑 / 不属于」。

**Q57. 为什么 Swagger 是 mobile-gateway 文档，user-service 不直接暴露 REST？**  
Swagger 面向 App 的 HTTP 契约，gateway 做鉴权、token、路由聚合。user-service 是内部 gRPC 用户中心，避免双份 API 与泄漏 DB 细节。

**Q58. 设备匿名登录怎么设计？**  
用 deviceId+platform 归一化后算 identity_hash，查 auth 表；没有则四表创建。复登同一 hash 命中 user_id，upsert 设备并更新 last_login，返回 newlyCreated 和 pending。

**Q59. 手机号登录为什么仍然用 identity_hash？**  
与 Register 一致，手机号不明文索引；验证码只做 mock 校验，通过后仍按 PHONE identity 查或建用户，安全模型统一。

**Q60. 三方登录为什么不能长期依赖 idToken？**  
idToken 会过期且不应入库。生产应由 gateway verify 后传稳定 subject/openId，user-service 只 hash 稳定身份；当前阶段 mock hash idToken 做联调。

**Q61. onboarding 和 UpdateProfile 有什么区别？**  
Onboarding 是首次补齐 gender/birthday 等必填，推 profile_status；UpdateProfile 是日常 PATCH，字段可选、校验更松。两者都删四类 Redis 缓存。

**Q62. age 和 birthday 怎么处理？**  
birthday 为源字段，Service 用 ProfileBirthdayParser 解析，ProfileAgeResolver 计算/校验 age，写入 profiles 供 Swagger 展示。

**Q63. Avatar upload 为什么分 presign 和 confirm？**  
Presign 只签发 PUT URL 和 objectKey，客户端直传 MinIO；Confirm 时 statObject 证明上传成功再落库，避免空 key。

**Q64. presign 为什么不落库？**  
用户可能放弃上传；落库会产生脏 photos。Confirm 成功后再写 user_photos 和 avatar_key。

**Q65. objectKey 为什么必须服务端生成？**  
统一 `avatar/{userId}/...` 前缀，Confirm 时可校验归属，防止客户端写别人目录。

**Q66. confirm 为什么要校验 objectKey 属于当前用户？**  
防越权绑定他人文件；校验前缀 + statObject，失败返回 AVATAR_OBJECT_NOT_BELONG_TO_USER。

**Q67. 为什么不做 home_card 组合缓存？**  
key 形如 self:target，target 资料更新无法精准失效所有 viewer 的 key，易脏读；当前 GetHomeCardProfile 直查 DB。

**Q68. HomeCard 为什么不校验 match 关系？**  
match 状态在 match-service；user-service 只回答 target 资料和账号是否可展示，gateway 可先调 match 再调 HomeCard 或并行编排。

**Q69. Redis 失败为什么不能影响主流程？**  
缓存是加速层不是 source of truth；Redis 挂了仍应能登录写库，CacheSafeExecutor 捕获异常降级读 DB。

**Q70. 你怎么做日志脱敏？**  
统一 SensitiveLogUtil：phone 掩码、smsCode/idToken 占位或截断、presignedUrl 不 full print、identityHash 短 hash；慢调用只打白名单字段。

**Q71. USER-09 最大的技术难点是什么？**  
在不动 gateway 的前提下，把 Swagger 多条 REST 链路拆成职责清晰的 gRPC，并统一 identity、缓存失效和错误码，还要保持与 USER-01～08 行为兼容。

**Q72. 这个模块怎么支撑前端 Swagger？**  
gateway 把 REST 转成 gRPC 调用：login-device→ResolveOrCreateDeviceUser，onboarding→UpsertOnboarding，upload→Presign/Confirm，home/card→GetHomeCardProfile；token 仍在 gateway 生成。
