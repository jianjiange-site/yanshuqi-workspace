# user-service 学习复盘

面向「学完 USER-01～USER-08 后想讲清楚这个模块」的读者。

---

## 我在 user-service 学到了什么

1. **微服务用户中心**的典型边界：注册/登录校验/资料/照片 key/批量读，不做 JWT 和网关 REST。
2. **gRPC 内部分层**：Grpc → DTO → Service → Manager → Mapper，职责比单体 MVC 更细。
3. **安全默认值**：密码 BCrypt、身份 hash 查重、日志脱敏、错误码不泄露堆栈。
4. **读多写少优化**：批量资料用 Redis cache-aside，写路径删缓存。
5. **可验收的工程习惯**：每阶段 checklist + 集成脚本 + 单元测试，而不是「能跑就行」。

---

## 注册为什么要四表事务？

一次注册要同时有：主账号（users）、登录凭证（auth）、资料壳（profiles）、默认设置（settings）。四表缺一则后续登录或资料接口无数据。放在**同一本地事务**里保证原子性；失败则全部回滚，不会出现「能登录但没资料」的脏状态。

---

## 登录为什么不签发 JWT？

user-service 定位是**身份校验与资料服务**，不是会话中心。JWT 由 gateway 统一签发，便于多端、刷新、踢下线（配合 `token_version`）。VerifyLogin 只回答「密码对不对、账号能不能用」，返回 `user_id` 等事实，gateway 再发 token。

---

## 为什么手机号 / 邮箱不能明文查？

明文进索引有泄露风险，且日志/备份容易带出。归一化后算 `identity_hash` 做唯一约束和登录查询；对外展示用脱敏 `identity_value`。这是 dating 类产品的常规隐私设计。

---

## 为什么用户资料和用户主表分开？

`users` 管账号生命周期（封禁、删除、资料完成度状态）；`user_profiles` 管展示字段。分离后：批量读可以只查 profiles + 少量 users 字段；资料大改不影响 auth 表；未来扩展设置、审核字段更清晰。

---

## 为什么头像只保存 object key？

上传在客户端或媒体服务完成，user-service 不碰 MinIO。只绑定 `object_key` 表示「这张图属于该用户」，gateway/CDN 负责拼 URL。审核状态在 `user_photos.review_status`，外显时过滤 PENDING。

---

## 为什么批量查询要用 Redis cache-aside？

推荐页、匹配列表会**高频批量拉**同一批 user_id。直打 DB 压力大。cache-aside：先读缓存，miss 再批量 IN 查库并回填；资料变更删 key，避免长期脏读。Redis 挂了仍可读库，只是慢一点。

---

## 为什么下游服务不能直接查 user-service DB？

破坏服务边界：schema 变更会拖垮所有调用方；无法统一做缓存、脱敏、审核过滤；违反「数据库私有」的微服务原则。正确方式是 gRPC 批量接口 + CheckUserAvailable。

---

## 为什么 gRPC 层不能写业务逻辑？

Grpc 层应只做：参数校验、DTO 转换、调 Service、异常映射。业务写在 Service 才能单测、复用，且避免「一个 Rpc 方法几百行」难以维护。本项目 `UserAuthGrpcService` / `UserProfileGrpcService` 保持薄。

---

## 为什么 Manager 禁止跨表编排？

Manager = 单表领域封装（CRUD + 单表规则）。跨表注册、批量聚合属于 **Service 职责**。这样 Manager 可复用，单元测试边界清楚，也避免循环依赖。

---

## 为什么 Redis 失败不能影响主流程？

缓存是**性能优化层**，不是事务参与者。get 失败当 miss；set/delete 失败只打 warn。写库成功即业务成功，避免 Redis 抖动导致用户改不了资料。

---

## 这个模块面试怎么讲

**30 秒版**：user-service 是 dating 产品的用户中心，gRPC 提供注册、登录校验、资料维护、照片 key 绑定和批量读；六张表单表 Mapper，Service 聚合；Redis cache-aside 600 秒；统一错误码映射；不做 JWT 和推荐。

**2 分钟版**：按「边界 → 注册事务 → 登录与设备 → 资料评分 → 照片审核外显 → 批量缓存 → 异常日志」顺序讲，每点带一个具体字段或 key 名。

**深挖准备**：identity_hash、token_version、profile_status 状态机、APPROVED 头像过滤、CacheSafeExecutor 降级。
