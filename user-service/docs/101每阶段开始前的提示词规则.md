# USER-Service 标准三模板系统

## 模板 1：GPT 阶段计划生成模板

使用场景：
每进入 USER-Service 的一个新阶段前，先把这段发给 GPT，让 GPT 生成当前阶段的详细技术方案和 Cursor 执行提示词。

```text
现在进入 ChatVibe / Dating App 项目的 user-service 模块开发。

当前阶段：
【填写阶段名称，例如：USER-01：用户基础表与实体】

项目固定约束：

1. 项目根目录结构为：
   yanshuqi-workspace/
   ├── ai-chat/
   ├── mobile-gateway/
   ├── user-service/
   ├── match-service/
   ├── im-service/
   ├── post-service/
   ├── payment-service/
   ├── example-service/
   ├── proto/
   ├── deploy/
   ├── scripts/
   ├── docs/
   └── study-docs/

2. user-service 包名固定为：
   com.dating.user

3. PostgreSQL：
   database = dating_dev_yanshuqi
   schema = user_center

4. Redis key 前缀：
   yanshuqi:user:

5. Nacos：
   namespace = yanshuqi-dev
   Data ID = user-service-dev.yaml

6. Java 技术栈：
   Java 21
   Spring Boot 3.3.5
   MyBatis-Plus
   PostgreSQL 16
   Redis 7
   Flyway
   gRPC
   Nacos

7. 开发规范：
   - Controller / gRPC 只做入口和参数转换
   - Service 负责业务编排和事务边界
   - Manager 负责单聚合数据访问编排
   - Mapper 只允许单表操作
   - 禁止多表 JOIN
   - 禁止跨服务直连数据库
   - 禁止服务间 HTTP 互调
   - 跨服务只能通过 gRPC
   - 禁止真实密码、Token、AK、SK、Secret 入仓库
   - 所有 public 方法必须写中文 Javadoc
   - 核心业务逻辑块必须写编号中文注释
   - 数据库表和字段必须写 COMMENT 中文注释

当前模块技术方案概要：

user-service 负责：
1. 用户账号创建
2. 登录凭证校验
3. 用户基础状态维护
4. 用户基础资料维护
5. 用户头像 / 相册 object key 绑定
6. 用户设备记录
7. 用户偏好设置
8. 用户资料完整度判断
9. 批量查询用户基础展示信息
10. 为 match-service / im-service / post-service / payment-service / ai-chat 提供用户基础数据 gRPC 查询能力

user-service 不负责：
1. 不签发 JWT，JWT 由 mobile-gateway 负责
2. 不负责推荐匹配，match-service 负责
3. 不负责聊天会话，im-service 负责
4. 不负责金币账户，payment-service 负责
5. 不负责 Feed 内容，post-service 负责
6. 不负责 AI 对话，ai-chat 负责
7. 不直接调用 OpenIM
8. 不访问其他服务数据库

USER-Service 阶段规划：

USER-01：用户基础表与实体
USER-02：用户注册
USER-03：用户登录
USER-04：用户资料维护
USER-05：头像 / 相册 object key 维护
USER-06：批量查询用户资料 gRPC
USER-07：缓存、异常、日志完善
USER-08：模块验收与复盘

请你基于以上约束，为当前阶段生成一份“阶段执行计划”。

输出要求：

## 1. 当前阶段目标

说明这个阶段到底解决什么问题。

## 2. 当前阶段业务范围

说明本阶段要做什么。

## 3. 当前阶段不做什么

明确禁止 Cursor 提前实现哪些后续阶段内容。

## 4. 涉及文件清单

按目录说明预计要新增 / 修改哪些文件。

## 5. 数据库设计

如果本阶段涉及数据库，必须说明：
- 表名
- 字段
- 主键
- 业务主键
- 唯一索引
- 普通索引
- created_at / updated_at / deleted
- COMMENT 中文注释要求

如果本阶段不涉及数据库，也要明确说明“不涉及数据库变更”。

## 6. Redis 设计

如果本阶段涉及 Redis，必须说明：
- key 格式
- TTL
- 写入 / 删除时机

如果不涉及 Redis，也要明确说明“不涉及 Redis 变更”。

## 7. 接口 / gRPC 设计

如果本阶段涉及接口，说明：
- 是否是 gRPC
- 请求参数
- 返回参数
- 异常场景

如果不涉及接口，也要明确说明“不定义正式接口”。

## 8. 核心调用链

用箭头写清楚：

入口 → gRPC / Controller → Service → Manager → Mapper → PostgreSQL / Redis

## 9. 技术难点

说明本阶段最容易写错的点。

## 10. 验收标准

给出可执行的验收清单。

## 11. 人工检查点

告诉我作为学习者要重点检查哪些代码。

## 12. Cursor 可执行提示词

最后生成一段可以直接复制给 Cursor 的完整执行提示词。

注意：
- 不要直接写业务代码
- 不要跳阶段
- 不要让 Cursor 一次性实现整个 user-service
- 当前阶段只做当前阶段范围
```

## 模板 2：Cursor 阶段执行模板

使用场景：
GPT 生成当前阶段执行计划后，把这个模板和 GPT 输出的“Cursor 可执行提示词”一起发给 Cursor。Cursor 负责写代码，但必须按模板输出阶段报告。

```text

当前阶段：
【填写阶段名称，例如：USER-01：用户基础表与实体】

当前阶段执行方案：
【粘贴 GPT 生成的当前阶段执行计划】

项目强约束：

1. 当前只允许修改 user-service 模块，以及与当前阶段直接相关的 docs / scripts。
2. 禁止修改 match-service、im-service、post-service、payment-service、mobile-gateway、ai-chat 的业务代码。
3. user-service Java 包名必须保持：
   com.dating.user
4. 禁止使用：
   com.chatvibe.*
   com.dating.yanshuqi.*
5. PostgreSQL：
   database = dating_dev_yanshuqi
   schema = user_center
6. Redis key 前缀必须是：
   yanshuqi:user:
7. 禁止跨服务直连数据库。
8. 禁止服务间 HTTP 互调。
9. 禁止多表 JOIN。
10. 禁止创建当前阶段未声明的业务表。
11. 禁止提前实现后续阶段功能。
12. 禁止提交真实密码、Token、AK、SK、Secret。
13. 所有 public 方法必须写中文 Javadoc。
14. 核心业务逻辑块必须写编号中文注释。
15. 数据库表和字段必须写 COMMENT 中文注释。

17. Controller / gRPC 只做入口和参数转换。
18. Service 负责业务编排和事务边界。
19. Manager 负责单聚合数据访问编排。
20. Entity 不允许直接作为对外返回对象。

执行要求：

## 一、开发前计划

7. 当前阶段不会做哪些内容

## 二、代码实现

按当前阶段执行方案实现代码。

要求：

1. 不要一次性修改无关模块。
2. 不要为了跑通写死关键业务逻辑。
3. 不要隐藏异常。
4. 核心逻辑必须写中文注释。
5. public 方法必须写中文 Javadoc。
6. SQL 表和字段必须有中文 COMMENT。
7. 如果发现现有设计不合理，先说明问题，再修改。
8. 如果当前阶段信息不足，可以基于合理假设继续推进，但必须在总结中明确假设。

## 1. 本阶段实现了什么

→ Mapper

## 6. Redis 变更

1. key 格式

4. 异常情况
```

## 模板 3：GPT 阶段验收模板

使用场景：
Cursor 执行结束后，把 Cursor 的完整阶段报告粘贴给 GPT，用这个模板让 GPT 做验收。GPT 要判断是否通过、哪里有风险、是否能进入下一阶段。

```text
下面是 Cursor 完成的 user-service 当前阶段开发报告。

请你作为 ChatVibe / Dating App 项目的技术导师，帮我做一次阶段验收和复盘。

我的目标：
不是只知道代码能跑，而是要真正理解这个阶段的业务流、代码调用链、数据流、技术点和风险。

当前阶段：
【填写阶段名称，例如：USER-01：用户基础表与实体】

Cursor 输出内容：
【粘贴 Cursor 阶段完成总结、变更文件、运行结果、错误日志等】

请你按照以下结构输出验收结果：

# 阶段验收报告：【当前阶段名称】

## 1. 验收结论

只能给出以下三种之一：

- 通过，可以进入下一阶段
- 有小问题，修正后可以进入下一阶段
- 不通过，必须返工

并说明原因。

## 2. 本阶段实现的业务流是什么

用业务语言总结这个阶段做了什么。

如果本阶段是基础建设阶段，也要说明它为后续哪个业务流做准备。

## 3. 完整代码调用链还原

按真实执行顺序说明：

入口文件
→ 方法
→ Service
→ Manager
→ Mapper
→ PostgreSQL / Redis
→ 返回结果

如果当前阶段没有业务入口，也要说明当前类未来会出现在什么调用链中。

## 4. 数据流还原

说明：

1. 数据从哪里来
2. 中间经过哪些对象
3. 是否入库
4. 入库到哪些表
5. 是否进入 Redis
6. 最终返回给谁

## 5. 架构边界检查

逐项判断：

1. 是否只修改了当前阶段允许范围
2. 是否跨服务修改代码
3. 是否出现服务间 HTTP 互调
4. 是否出现跨服务直连数据库
5. 是否出现多表 JOIN
6. 是否 gateway 写业务逻辑
7. 是否 ai-chat 访问 Java 服务数据库
8. 是否提前实现后续阶段功能

每项必须给出：通过 / 不通过 / 未涉及。

## 6. 数据库设计检查

如果涉及数据库，检查：

1. 是否在 user_center schema
2. 是否有业务主键
3. 是否有 created_at / updated_at / deleted
4. 是否使用 TIMESTAMPTZ
5. 表是否有 COMMENT
6. 字段是否有 COMMENT
7. 索引是否合理
8. 是否存在敏感字段明文风险
9. 是否违反单表操作原则

如果不涉及数据库，说明“本阶段不涉及数据库”。

## 7. Redis 规范检查

如果涉及 Redis，检查：

1. key 是否以 yanshuqi:user: 开头
2. 是否设置 TTL
3. 是否有永久 key
4. 是否有 FLUSHDB / FLUSHALL 风险
5. 是否符合 cache aside 策略

如果不涉及 Redis，说明“本阶段不涉及 Redis”。

## 8. 注释规范检查

检查：

1. public 方法是否有中文 Javadoc
2. Javadoc 是否包含用途、入参、返回值、异常
3. 核心业务逻辑块是否有编号中文注释
4. 是否存在无意义注释
5. SQL 表和字段是否有中文 COMMENT

## 9. 当前实现的优点

只说真实优点，不要泛泛夸。

## 10. 当前实现的问题和风险

直接指出，不要只说优点。

- 问题：
```
