# user-service 数据模型复盘

Schema：`user_center`（库 `dating_dev_yanshuqi`）。业务主键统一为 `user_id`（Snowflake），跨表关联均用 `user_id`，禁止 Mapper JOIN。

---

## 六张核心表

### users — 用户主表

保存用户全局状态：`user_type`、`account_status`、`profile_status`、`register_source`、`token_version`、`last_login_at`。注册时创建，登录时更新 `last_login_at`，资料/照片绑定更新 `profile_status`。

### user_auth_identities — 登录凭证表

保存 `identity_type` + `identity_hash` + `password_hash`。注册创建一条凭证；登录按 hash 查询。`identity_value` 存脱敏展示值，**禁止日志明文**。

### user_profiles — 用户资料表

昵称、性别、生日、地区、语言、bio、兴趣、`profile_score`、`profile_completed`、`avatar_key`（冗余当前头像 key，便于本人资料快速读取）。

### user_photos — 用户照片表

`photo_type`（AVATAR/ALBUM）、`object_key`、`sort_order`、`review_status`（PENDING/APPROVED/REJECTED）、`enabled`。支持历史头像（旧头像 disabled）和相册多图。

### user_devices — 用户设备表

`platform`、`device_fingerprint`、`push_token_hash`、`app_version`、`last_seen_at`。登录时 upsert，用于推送与风控，**不返回给下游批量接口**。

### user_settings — 用户设置表

注册时写默认记录（如 `discoverable`）。本阶段业务 RPC 未暴露设置修改，表已预留扩展。

## 关键设计问题

### user_id 如何贯穿全部表？

注册生成一个 `user_id`，四表（users/auth/profiles/settings）同事务写入同一 ID。后续登录、资料、照片、设备均以 `user_id` 为外键逻辑关联（物理上无 FK 跨服务，库内为业务约束）。

### identity_hash 为什么存在？

手机号/邮箱不能明文做唯一索引和等值查询。归一化后 SHA-256 得到 `identity_hash`，用于「是否已注册」和「登录查凭证」，日志与对外接口均不暴露 hash 原文语境下的敏感信息。

### password_hash 为什么存在？

密码只存 BCrypt 哈希，注册时 `PasswordHashService.hash`，登录时 `matches`。明文密码不进库、不进日志、不进 gRPC 响应。

### avatar_key 为什么冗余在 user_profiles？

本人资料 `GetSelfProfile` 需要快速返回当前绑定头像 key，不必每次 JOIN/聚合 `user_photos`。绑头像时同步更新 `user_profiles.avatar_key`；**外显批量查询**仍从 `user_photos` 取 APPROVED 头像，与冗余字段解耦。

### user_photos 如何支持历史头像和相册？

- 头像：新绑定前 `disableCurrentAvatar`，仅一条 `enabled=1`；历史记录保留 `enabled=0`。
- 相册：`photo_type=ALBUM`，`sort_order` 排序，上限 20 张。
- 外显：仅 `enabled=1 & review_status=APPROVED & photo_type=AVATAR`。

### user_devices 为什么在登录时 upsert？

同一 `user_id + device_fingerprint` 不重复插入；更新 `last_seen_at` 与 `push_token_hash`，支撑推送与多设备管理。

### Mapper 为什么禁止 JOIN？

- 单表职责清晰，便于分阶段演进与单表缓存。
- 批量查询在 Service 层按 `user_id` 合并三表结果，灵活控制外显规则（如审核头像过滤）。

### Service 层为什么负责聚合？

Manager 只做单表；跨表编排（注册四表、批量合并 users/profiles/photos、可用性判断）属于业务，放 Service。gRPC 层不做 DB/Redis。

## 逻辑删除

各表 `deleted` 字段：0 正常，1 已删除。MyBatis-Plus 逻辑删除插件统一过滤。
